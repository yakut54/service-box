# ServiceBox — Plan

## ⚠️ Правила работы с миграциями

**Миграционных файлов быть не должно.** Порядок работы с любым изменением схемы БД:

1. Создать миграцию → применить на сервере (`php artisan migrate`)
2. Проверить что всё работает
3. Внести изменения в `database/schema/pgsql-schema.sql`
4. **Удалить файл миграции нахуй**

Файлы миграций — мусор. Из-за них происходят несоответствия между схемой и реальной БД.

## Стек

- **Backend:** Laravel 11, PostgreSQL 16 (multi-tenant schemas), Redis, Sanctum
- **Frontend:** Vue 3 + TypeScript, Tailwind CSS (admin), Pinia, Vite
- **Infrastructure:** Docker, Nginx, GitHub Actions (deploy on push to `new-branch`)
- **Server:** root@31.128.39.216, app `/var/www/servicebox/`, домен `https://yakut54.ru`
- **Queue driver:** `sync` (нет async-очередей — все операции синхронные)

## Архитектура

```
servicebox/
├── app/              — Laravel API
├── admin/            — SPA для владельца магазина (Vue 3)
├── widget/           — Встраиваемый виджет для сайта клиента (Vue 3, Shadow DOM)
└── database/         — schema/pgsql-schema.sql (единственный источник истины по схеме БД)
```

Каждый магазин — отдельная PostgreSQL-схема `shop_{id}`. Таблицы `customers`, `products`, `orders`, `bookings`, `masters` и др. изолированы per-tenant.

### ⚡ Закон синхронизации — обязателен для каждого этапа

**Любое действие в любом из трёх каналов (TG / MAX / сайт) должно немедленно отразиться во всех трёх.**

| Действие | TG бот | MAX бот | Сайт (автополлинг) |
|---|---|---|---|
| Клиент оставил оценку | Шопер + мастер уведомлены | Шопер + мастер уведомлены | Отзыв появился в ReviewsView |
| Клиент перенёс запись | Кнопки убраны, шопер + мастер уведомлены | Кнопки убраны, шопер + мастер уведомлены | Запись = cancelled в BookingsView |
| Шопер отправил win-back | Клиент получил (если есть TG) | Клиент получил (если есть MAX) | — (нет нужды) |
| Клиент записался после win-back | Шопер + мастер уведомлены | Шопер + мастер уведомлены | Новая запись в BookingsView |

**Следствия:**
- Если действие произошло в TG → кнопки в MAX тоже убираются (`removeButtons`)
- Если действие произошло в MAX → клавиатура в TG тоже убирается (`removeKeyboard`)
- Уведомления шоперу/мастеру всегда уходят в **оба** бота независимо от канала-источника
- Состояние в DB всегда первично — сайт читает из DB, боты пишут в DB

### Серия W — Win-back

> Клиент давно не приходил → шопер узнаёт об этом в боте → одним нажатием отправляет напоминание.
> Конкуренты: нет ни у кого нативно через Telegram/MAX.
> По данным beauty-индустрии win-back поднимает retention на 20-30%.

#### Архитектура

- **Порог**: клиент не приходил 60 дней (считаем по последней `completed` записи)
- **Условия**: у клиента есть `telegram_chat_id` или `max_user_id` (иначе нечем напомнить)
- **Антиспам**: `Cache::put("winback:{shopId}:{customerId}", true, now()->addDays(30))` — раз в 30 дней
- **Запуск**: `bookings:winback` artisan → `Kernel.php` → `dailyAt('04:00')` UTC ≈ 11:00 NSK
- **Синхронизация**: если клиент записывается по ссылке → стандартный flow (уведомления шоперу/мастеру как обычно)

### Безопасность
- X-API-Key валидируется через TenantService::setContextByApiKey()
- Rate limit: 60 req/min global + 20 req/min для POST-мутаций per API key
- Заголовки: X-RateLimit-Limit, X-RateLimit-Remaining; 429 → Retry-After
- ForceJson middleware: принудительный Accept: application/json — предотвращает 302-редирект при ошибках валидации
- Доступно только на тарифе Pro (feature gate: `api_access`)
