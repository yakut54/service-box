## ⚠️ Правила работы с миграциями

**Миграционных файлов быть не должно.** Порядок работы с любым изменением схемы БД:

1. Создать миграцию → применить на сервере (`php artisan migrate`)
2. Проверить что всё работает
3. Внести изменения в `database/schema/pgsql-schema.sql`
4. **Удалить файл миграции нахуй**

Файлы миграций — мусор. Из-за них происходят несоответствия между схемой и реальной БД.
Новая колонка = обновить `create_shop_schema()` (для новых схем) **и** `ALTER TABLE
IF NOT EXISTS` (для существующих) — одним коммитом со сверкой схемы.

## Стек

- **Backend:** Laravel 11 (PHP 8.2), PostgreSQL 16 (multi-tenant schemas), Redis, Sanctum
- **Admin / Widget:** Vue 3 + TypeScript + Vite, Tailwind, Pinia. Админка с роутером, виджет без (один магазин на странице)
- **Mobile:** Flutter, `provider` + `ChangeNotifier`. White-label: один флейвор сборки = один шопер
- **Infrastructure:** Docker, Nginx, GitHub Actions (деплой по пушу в `flutter-app`)
- **Server:** `root@193.168.49.102`, app `/var/www/servicebox/`, домен `https://yakut54.ru`
- **Queue driver:** `database` (2026-08-29) — контейнер `servicebox_worker`. Раньше был `sync` (реальный SMTP добавлял бы 1–3с к оформлению заказа прямо в HTTP-запросе)
- **Mail driver:** `smtp` через Beget (домен на почте Beget, SPF/DKIM готовы)

### Контейнеры (`docker-compose.prod.yml`) — 6 штук

| Контейнер | Что делает |
|---|---|
| `servicebox_app` | PHP-FPM, Laravel |
| `servicebox_web` | nginx, `8000:80` |
| `servicebox_db` | postgres:16-alpine. Проброшен на `127.0.0.1:5432` для локальных инструментов через SSH-туннель (DBeaver и т.п.) |
| `servicebox_worker` | `php artisan queue:work` — письма уходят фоном с ретраями |
| `servicebox_scheduler` | `php artisan schedule:work` — напоминания о записях, утренний дайджест, `orders:check-surcharge-deadline` |
| `servicebox_reverb` | `php artisan reverb:start --port=6001` — WebSocket для чата. **Только в prod-компоузе**, в dev-`docker-compose.yml` его нет |

Плюс `TELEGRAM_SECRET_TOKEN` пробрасывается в контейнер `app` через деплой-скрипт.

```
service-box/
├── app/                — бэкенд, Laravel 11. Модели, контроллеры, сервисы, middleware
├── admin/              — SPA админки для шоперов (Vue 3 + Pinia + Vue Router)
├── widget/             — SPA виджета для байеров, встраивается на сайт шопера (Vue 3, без роутера)
├── mobile/             — приложение байера, Flutter. White-label, один флейвор = один шопер (mobile/README.md)
├── database/schema/    — pgsql-schema.sql, единственный источник истины по схеме БД
├── page-api-example/   — демо-страница внешнего API v1 + docs.html
├── .github/workflows/  — deploy.yml (единственный workflow)
├── deploy.sh           — реальная логика деплоя (см. «Деплой»)
├── docker-compose.yml / docker-compose.prod.yml
├── PLAN.md             — этот файл
└── PLAN-CHAT.md        — отдельный подробный план по чату «шопер ↔ байер»
```

**Мультитенантность:** одна Postgres-схема на магазин (`shop_<id>`), общие таблицы
(`shops`, `shop_staff`, `shop_features`, `customers`-аутентификация) — в `public`.
`TenantService::setContext()` / `setContextByApiKey()` переключает `search_path`
перед каждым запросом. Таблицы `customers`, `products`, `orders`, `bookings`,
`masters`, `chat_*` изолированы per-tenant.

**Шоперы** — наши клиенты (владельцы магазинов, админка). **Байеры** — клиенты
шоперов (покупатели, виджет + мобилка). На бэкенде разделены: `/api/admin/*`
(Sanctum) и `/api/widget/*` (`X-Shop-ID` + api-key) — разные middleware-стеки.
Роли внутри шопера — `shop_staff.role`: `owner` / `admin` / `master` / `collector`,
урезание доступа через allow-list middleware (`RequireNotMaster`,
`RequireCollectorAccess`), а не проверки роли по всему коду.

**Таймзона** — `shops.timezone`, настраивается шопером. Всё, что связано со
временем, опирается на неё (`Carbon::now($shop->timezone)`), не на таймзону
сервера или браузера.

## 🎯 Концепция: Флот Шоперов (пивот 2026-08-18)

Один бэкенд, одна мультитенантная база. До ~10 шоперов, ни один не знает про
остальных. У каждого — **своё отдельное APK** на RuStore со своим брендом, именем,
иконкой. Байер магазин не выбирает — приложение с рождения знает только своего
шопера. Конкуренты в нише (Altegio, DIKIDI) продают ровно такую white-label
модель как платную фичу.

- **Один APK = один шопер.** `api_key` магазина зашивается на сборке через Flutter
  **flavors** + `--dart-define` (`mobile/flavors/<flavor>.json`, читается через
  `FlavorConfig`). У каждого флейвора свой `applicationId`, имя, иконка, splash.
  Сейчас заведён один флейвор — `barbariska` (`shop_xdirmgfxyd7u`).
- **Бэкенд общий, концептуально не меняется** — приложение ходит в те же
  `/widget/*` эндпоинты, что и веб-виджет, с уже зашитым `X-Shop-ID`.
- **Фича-флаги (entitlements)** — таблица `public.shop_features (shop_id,
  feature_key, enabled)`, дефолт `false`. `Shop::hasFeature($key)`. Middleware
  `feature:<key>` гейтит роут на бэкенде (что отдаёт API). Ключи сейчас:
  `booking`, `digital_goods`. Флаги пока ставятся только руками в БД — UI нет
  (МФ5, см. «Что осталось»).
- **Dark launch:** код новой платной фичи (вместе с UI-экранами) катится во **все**
  флейворы сразу, выключенным флагом. Шопер заплатил → щёлкаем флаг в мастер-админке
  → фича включилась без новой сборки и заливки в RuStore. Пересборка APK нужна
  только один раз — когда код фичи впервые попадает в приложение.
- Обновление APK прилетает всем пользователям всех магазинов, скачивают все, но
  фичу видят только те, у кого флаг включён.
- **Дистрибуция — RuStore** (не Google Play, iOS не рассматриваем). Первая версия
  каждого шопера — вручную через консоль; последующие обновления — CI/CD (МФ7).

Готово: пивот Flutter-кода (выброшены онбординг/сканер/switcher), flavors, таблица
`shop_features`, `hasFeature()`, middleware `feature:`, фильтр digital/service в
`ProductController` (только виджет-контекст). Детали — в архиве, раздел
«Мобильное приложение — Флот Шоперов».

## 🔜 Push-уведомления — план внедрения

> Полное обоснование, разбор конкурентов и best practice UI/UX — `push-notifications-research.pdf`
> в корне (не в git). Ниже — пошаговый план. Каждый шаг: реализация → коммит+пуш
> (деплой авто) → **стоп** → проверка. Не копить шаги.
>
> **Что уже есть:** FCM подключён per-flavor, `FcmService` шлёт токен на
> `POST /widget/profile/fcm-token`, `customers.fcm_token` (одно поле). `FirebaseService`
> написан, выключен (нет `FIREBASE_CREDENTIALS_PATH`). Единственный вызов push —
> `OrderReweighService` (доплата). Другие каналы: Telegram, MAX, email, in-app баннер.
>
> **Сквозные правила для всех шагов:** отправка — только в очередь (`servicebox_worker`),
> никогда в HTTP-запросе; в джобу — массив, не Eloquent (тенантный `search_path`);
> суммы через `App\Support\Money::rubles()`; время — в `shops.timezone`; текст — на языке
> пользователя; push = сигнал (в payload только id + минимум текста).

### Шаг 2 — Включить канал: серверные креды Firebase ✅ (2026-09-06)
- **Сделано.** `FIREBASE_CREDENTIALS_PATH` проброшен в `docker-compose.prod.yml` → `app`, `worker`, `scheduler`. `.env.example` описывает, куда класть JSON; `.gitignore` — `/firebase-credentials.json` и `/needs/` (локальная папка для секретов/исследований). Сервис-аккаунт `firebase-adminsdk-fbsvc@servicebox54.iam.gserviceaccount.com` залит в `/var/www/servicebox/firebase-credentials.json` (в контейнере `/var/www/html/firebase-credentials.json`), строка в `.env` на сервере. `deploy.sh` и так делает `config:cache` каждый деплой → переменная подхватывается.
- **Три латентных бага, вылезли при включении канала (раньше `messaging()` был null и до них не доходило):**
  1. `CloudMessage::withTargetToken()` не существует в kreait 7.x → `CloudMessage::withTarget('token', …)`.
  2. Битый токен kreait 7.x кидает `Messaging\InvalidMessage` («The registration token is not a valid FCM registration token»), а не `NotFound`/`InvalidArgument` — классификация ошибок в `send()` переписана: `NotFound` + `InvalidMessage`-про-токен → `InvalidToken` (удаляем строку); `InvalidMessage`-про-payload → `TransientError` + error-лог; `AuthenticationError` → `TransientError` + громкий лог.
  3. `config:cache` был построен до появления переменной в `.env` — `config('services.firebase.credentials_path')` возвращал пусто; пересобрал.
- **Проверено на сервере.** `FirebaseService::configured()` → `TRUE`. `send()` на заведомо битый токен → `InvalidToken` (значит креды реально аутентифицируются в FCM, Google принял запрос и отверг только токен). `push_failures` пуст.
- **Не проверено:** реальная доставка push на физическое устройство — нужен настоящий device-token (появится на Шаге 3, когда соберём APK и войдём с телефона).

### Шаг 4 — Транзакционные push: статус заказа
- **Что.** События на бэкенде (`OrderController::updateStatus`, вебхук ЮKassa, `OrderReweighService`): принят / оплачен / оплата не прошла / собирается / готов / передан курьеру / в пути / доставлен / отменён. Каждое → джоба → `FirebaseService` с `collapse_key = order:{id}:status`, priority high, канал «Заказы»/«Доставка». Текст: имя + №заказа + статус, сумма через `Money`. Payload: `{type:'order_status', order_id}`. Мобилка: обработчик диплинка регистрируется до отрисовки первого экрана (cold start!), тап → экран заказа; протухший заказ → понятное состояние, не ошибка.
- **Стоп.** Смена статуса тестового заказа → корректный русский push, тап открывает нужный заказ и при холодном старте (приложение убито).
- **Коммит.** `feat(push): order status notifications with deep link`
- **Проверка.** Заказ на тестовом шопе. В админке менять статусы по очереди → на каждый приходит push с верным текстом и суммой в рублях. Устройство офлайн, сменить 3 статуса, включить сеть → пришёл только последний (`collapse_key`). Убить приложение, тап по push → открылся этот заказ, не главная.

### Шаг 6 — Оркестратор каналов: один канал на событие + фолбэк + кап частоты
- **Что.** Единая точка «уведомить байера о событии X». Выбор канала: **push → (нет токена / `InvalidToken` / не доставлено) → Telegram → MAX → email → in-app при следующем заходе**. Трёхуровневый приоритет: Tier-1 транзакционные (вне лимита), Tier-2 поведенческие, Tier-3 кампании; при Tier-1 подавлять Tier-2/3 на 4 ч. Тег «заказал сегодня» на 24 ч исключает из промо. Единый счётчик частоты по **всем** каналам вместе (кап 2–3/день, транзакционные не считаются). Критичное (доплата) — разрешить два канала явно.
- **Стоп.** Одно событие уходит ровно в один канал; при мёртвом токене — фолбэк на Telegram; промо не уходит в день заказа.
- **Коммит.** `feat(push): single-channel orchestrator with fallback and cross-channel frequency cap`
- **Проверка.** Тестовый байер с привязанным Telegram. Событие «заказ готов» → пришло только в push (Telegram молчит). Обнулить токен в БД → то же событие → пришло в Telegram. Оформить заказ, тут же запустить промо-рассылку на этот сегмент → байер её не получил (тег). Отправить 5 промо подряд → дошло не больше капа.

### Шаг 7 — Центр настроек уведомлений в профиле байера
- **Что.** Экран в профиле мобилки: иерархия категория → тип → канал → частота. Транзакционные (статус заказа, доплата, оплата) — показаны с **выключенным** тумблером (видно, отключить нельзя). Маркетинг — **OFF по умолчанию**. Поведенческие — ON по умолчанию с лёгкой отпиской. Бэкенд: `customer_notification_prefs` (тенантная) + гейт в оркестраторе (Шаг 6).
- **Стоп.** Тумблеры сохраняются и реально гейтят отправку; транзакционные выключить невозможно.
- **Коммит.** `feat(push): in-app notification preference center`
- **Проверка.** Выключить «Акции» → промо-событие не пришло, «заказ готов» пришло. Транзакционные — тумблер серый/недоступен. Перезайти в приложение → настройки сохранились.

### Шаг 8 — Поведенческие триггеры
- **Что.** Брошенная корзина: джоба через 1–3 ч после последнего изменения непустой корзины без заказа, повтор +24 ч (не больше). Товар из избранного снова в наличии (по изменению `stock`). Снижение цены на просмотренный товар. Win-back — переиспользовать **Серию W** из архива (крон `bookings:winback` → обобщить на заказы). Все — Tier-2, тихие часы по таймзоне магазина, уважать настройки (Шаг 7) и кап (Шаг 6).
- **Стоп.** Каждый триггер срабатывает один раз в положенное окно, глушится настройкой и капом.
- **Коммит.** `feat(push): behavioral triggers — abandoned cart, back-in-stock, win-back`
- **Проверка.** Положить товар в корзину тестового байера, не оформлять → через окно пришёл push (проверять ускоренным окном на тесте). Оформить заказ до срабатывания → push не пришёл. Выключить «Акции» в настройках → не пришёл.

### Шаг 9 — Напоминания о записи на push + промо + мастер-админка
- **Что.** Когда у магазина включён флаг `booking`: `SendBookingReminders` шлёт ещё и push (каскад 24 ч / 2 ч), кнопки «Подтвердить»/«Перенести» (свести с **Серией П**), запрос оценки через 2 ч. Промо магазина: только по **явному согласию** (38-ФЗ, без предзаполненных галочек), ≤2/нед, тихие часы. Мастер-админка: тумблер магазина «Push покупателям» (транзакц., ON) и «Промо-push» (OFF, включает шопер, приняв условия рекламной рассылки), шаблоны промо с модерацией платформой. Хранить подтверждение согласия (152-ФЗ).
- **Стоп.** Напоминание о записи дублируется в push; промо уходит только магазинам с согласием и в рамках лимита.
- **Коммит.** `feat(push): booking reminders over push + merchant promo with consent`
- **Проверка.** Магазин с флагом `booking`, запись на завтра → `php artisan bookings:send-reminders` → пришло и в push, и в мессенджер. Магазин без согласия на промо → промо-рассылка ему недоступна в мастер-админке. С согласием — уходит, третья за неделю режется лимитом.

4. **Сборки Flutter APK / заливки в RuStore в CI нет** (см. МФ7)
5. Время деплоя — ~1 минута

Финальное решение — `Teleport` пузыря в `<body>`, позиционирование через `fixed` + координаты триггера, посчитанные в JS (`getBoundingClientRect`); видимость переведена с CSS `group-hover` на JS `mouseenter`/`focusin`, т.к. Teleport выносит пузырь из DOM-поддерева триггера. Компонент используется в ~12 местах, включая нетривиальный `RevenueChart.vue` (там `<UiTooltip>` — это ещё и flex-ячейка бара графика, передаёт классы прямо на компонент) — потребовался `inheritAttrs: false` + ручной `v-bind="$attrs"` на триггере.

### ⚡ Закон синхронизации — обязателен для каждого этапа

**Любое действие в любом из трёх каналов (TG / MAX / сайт) должно немедленно отразиться во всех трёх.**

| Действие | TG бот | MAX бот | Сайт (автополлинг) |

## 📱 Мобильное приложение — Флот Шоперов (white-label)

> **Пивот 2026-08-18.** Было: одно универсальное APK для всех байеров всех шоперов, с
> онбордингом/сканером QR/переключателем магазинов внутри приложения. Стало: у каждого
> шопера — своё отдельное APK, байер вообще не выбирает магазин, приложение с рождения
> знает только про своего шопера.
>
> **Причина:** шоперы не должны видеть и знать друг о друге (~10 шоперов запланировано,
> ни один не в курсе про остальных). Конкуренты в нише (Altegio, DIKIDI) уже продают ровно
> такую white-label модель как платную фичу — рынок подтверждён.
>
> **Только физические товары в MVP.** Услуги (`products_service`/bookings) и цифровые товары
> (`products_digital`) уже поддержаны в БД и никуда не делись — но НЕ показываются в новом
> мобильном приложении. Включаются точечно через entitlements, когда конкретный шопер за
> это платит — без единой правки кода на момент включения.
>
> Полная концепция и обоснование (архитектура, феча-флаги, дистрибуция, CI/CD) — артефакт
> «Флот Шоперов», опубликован в чате 2026-08-18.

### Архитектура

- **Один APK = один шопер.** `shop_code` (по факту — `api_key` магазина) зашивается на
  этапе сборки через Flutter **flavors** + `--dart-define`, не выбирается в рантайме.
- У каждого флейвора свой `applicationId`, имя, иконка — иначе Android не даст поставить
  наши же приложения рядом на одном телефоне.
- **Бэкенд не меняется концептуально** — приложение ходит в те же `widget/*` эндпоинты,
  что и сейчас веб-виджет, с уже зашитым `X-Shop-ID`. Отдельный `GET /app/{shop_code}` для
  рантайм-обнаружения магазина (старый М0.1/М0.2) **не нужен** — код магазина не вводится
  пользователем, он уже в сборке.
- **Entitlements** — новая таблица `shop_features (shop_id, feature_key, enabled)`. Гейтит
  booking/digital-goods и на бэкенде (что отдаёт API), и в приложении (какой UI показывать).
  Дефолт — все флаги `false`, кроме физ-товаров. Реальных шоперов в проде нет и не было
  никогда (см. `shop_omtgfybbrig5` — это тестовые данные), поэтому миграционная осторожность
  не нужна, дефолты можно менять свободно.
- **Dark launch:** код новой фичи (в т.ч. UI-экраны) катится во **все** флейворы сразу,
  выключенным флагом — включается позже щелчком в мастер-админке, без новой сборки/заливки
  в RuStore. Пересборка нужна только один раз — когда код фичи впервые попадает в приложение.
- **Дистрибуция — RuStore** (не Google Play; iOS пока не рассматриваем). CI/CD: GitHub
  Actions собирает APK матрицей по флейворам → заливает через RuStore Publisher API. Первая
  версия каждого нового шопера в RuStore — вручную через консоль (автоматизируются только
  последующие обновления).

#### М5 — Яндекс.Доставка

> Ключ от Яндекса всё ещё не выдан (ждём ответ поддержки) — **максимально подготовились
> без него**: изучили документацию (2026-08-20), завели место для настроек и каркас
> сервиса, чтобы при получении ключа осталось подключить и проверить, а не проектировать
> с нуля.

> **Базовый URL:** `https://b2b.taxi.yandex.net`
> **Авторизация:** `Authorization: Bearer <OAuth-токен>` — выдаётся в личном кабинете
> dostavka.yandex.ru → «Интеграция» → «Получить токен» (нужен логин от менеджера
> Яндекс.Доставки). Токен бессрочный, слетает только при смене пароля аккаунта.
> **Демо/песочница:** в документации не описана — по факту доступна только боевая среда.
> **Договор:** нужен для продакшена — регистрация на dostavka.yandex.ru как бизнес.

**Проверенные эндпоинты (документация: yandex.ru/support/delivery-profile/ru/api/express):**

| Метод | Что делает |
|---|---|
| `POST /v2/offers/calculate` | Цена + сроки. Оффер живёт ~10 мин (`offer_ttl` в ответе) — `claims/create` нужно успеть вызвать до истечения |
| `POST /v2/claims/create` | Создать заявку (`request_id` — идемпотентность, повтор с тем же значением не создаст дубль) |
| `POST /v2/claims/accept?claim_id=` | Подтвердить заявку — тело `{"version": N}`, версия из ответа create/info |
| `POST /v2/claims/info?claim_id=` | Статус — полный список статусов ниже |
| `POST /v2/claims/cancel-info?claim_id=` → `POST /v2/claims/cancel?claim_id=` | Отмена — сначала узнать условия (бесплатно/платно), потом отменить |

**Статусы claims/info.status** (для маппинга на `orders.status`): `new` → `estimating` →
`ready_for_approval` (можно `accept`) → `accepted` → `performer_lookup` →
`performer_found` → `pickup_arrived` → `pickuped` → `delivery_arrived` → `delivered` →
`delivered_finish`. Плюс ветки отказа: `estimating_failed`, `performer_not_found`,
`failed`, `cancelled*`.

**Архитектура интеграции (без изменений от прежнего плана):**
```
Клиент вводит адрес →
  Бекенд: POST offers/calculate (склад → адрес клиента) →
    Показать цену клиенту →
      Если order.total >= free_delivery_from (настройка шопера) → доставка бесплатно →
        Клиент оплачивает заказ →
          Бекенд: POST claims/create → POST claims/accept → курьер назначен
```

## ✅ Развесной товар — три режима продажи (ТЗ 2026-08-24, реализовано к 2026-08-31)

> **Предыстория (2026-08-18…21, свёрнута).** Изначально овощи/фрукты «Барбариски»
> были заведены как фасовка фиксированного веса. Исследование (Instacart,
> WooCommerce, документация ЮKassa) показало три модели развесной торговли:
> (A) штучный неделимый товар; (B) выбор веса ползунком, продавец фасует ровно
> под заказ — без перевзвешивания и второго платежа; (C) реально плавающий вес,
> перевзвешивание при сборке + доплата/возврат через двухстадийный платёж ЮKassa
> (списать меньше холда — штатно, больше — только вторым платежом).
>
> **Решение (2026-08-24):** нужны все три режима сразу, выбираются per-товар через
> `products_physical.sale_mode`. Ключевой трюк реализации — НЕ меняли
> `order_items.quantity` на `NUMERIC` (риск для всей существующей арифметики
> `price*quantity`), вместо этого для весовых строк `quantity=1` + уже посчитанная
> абсолютная цена позиции + отдельное `order_items.weight_grams` для отображения.
>
> **Статус: всё реализовано** — фундамент Ф1–Ф4 и режимы A/B (2026-08-24), режим C
> с холдами ЮKassa (2026-08-31, полный разбор — в разделе «Режим C» выше).

### Режим A — «Штучный товар» — ✅ сделано (было готово и раньше)

Целые неделимые плоды (арбуз целиком, лоток нарезки). По сути — текущее
поведение системы без изменений, просто явный тип вместо подразумеваемого по
умолчанию.

- Админка: тип «Штучный» → «Цена за штуку» → необязательно «Примерный вес» (переиспользовали уже существующее поле `weight_grams`, отдельное поле заводить не стали — оно и так никак не использовалось в логике доставки, только лежало неиспользуемым) ✅

### Режим B — «По весу, фиксированная фасовка» — ✅ сделано 2026-08-24

Продавец фасует ровно под заказ (конфеты, орехи, специи, крупы — основной
ассортимент «Барбариски»). Без перевзвешивания и без второго платежа — самый

- Админка: тип «По весу (фасовка)» → «Цена за кг» → «Шаг ползунка» (дефолт 100 г) → «Мин/макс вес» (дефолт 100 г / 5000 г) ✅

- Допуск ±5% от заказанного веса — это ответственность продавца при сборке, в код не превращается (не проверяется автоматически, это просто SLA-ожидание к продавцу)

### Режим C — «По весу, с перевзвешиванием» — ✅ сделано 2026-08-31

Товары с реально плавающим весом — точная фасовка физически невозможна
(свежие овощи/фрукты навалом, мясо, рыба). Требовал интеграции с
холдированием ЮKassa — самый сложный из трёх режимов, единственный, который
трогает оплату. Полный разбор — см. «✅ Режим C «По весу — перевзвешивание» —
полный рабочий цикл (2026-08-31)» выше. Отличия от исходного ТЗ ниже,
решённые в процессе реализации:

- **% запаса холда — не делали.** Холд создаётся ровно на заявленную сумму
  (вес × цена, без наценки). Проще для покупателя (видит ровно ту сумму, что
  и в обычном заказе) и не требует новой глобальной настройки платформы;
  цена «плавает» уже после — вторым платежом, если факт больше
- Покупатель: ползунок с примерной ценой (готово ещё с общего фундамента, Ф2) — отдельной пометки «финальная цена по факту» на виджете/мобилке не добавляли, статус заказа и экран деталей это отражают явно
- Сборщик вносит фактический вес — поле ручного ввода в `CollectorOrderDetailView.vue`, роль `collector` (была готова ещё раньше этой фичи)
- Расчёт по факту — как в ТЗ: факт ≤ холда → `capture` на факт; факт > холда → второй платёж на разницу, покупателю — Telegram/MAX + email + push (см. п.11 выше) + обратный отсчёт 3 часа в приложении; не подтвердил → `needs_attention` (крон `CheckSurchargeDeadline`)
- Позиция отменена сборщиком (товара нет) — ввод веса «0 г», отдельной кнопки не понадобилось (см. п.4 выше)
- Незахваченный холд при сбое ЮKassa — не строили отдельное уведомление продавцу; ошибка `capturePayment()` логируется (`Log::error`), выяснение — вручную по логам. Можно вернуться, если станет реальной проблемой на практике
- В истории заказа у покупателя — строка «Заявлено: X г → Факт: Y г» на экране деталей заказа (мобилка)

| 2 | Замерено вживую на тестовом сервере (GD внутри контейнера): при одинаковом quality=80 WebP вышел **в 2.4 раза легче JPEG** (121 КБ vs 289 КБ) на изображении с текстом/линиями/фигурами. Продовый JPEG-пайплайн, чтобы влезть в лимит 100 КБ, был вынужден ещё и **резать разрешение вдвое** (1024→512px) — WebP укладывается в лимит на полном разрешении | ✅ |
| 3 | `ImageCompressionService`: `imagejpeg()` → `imagewebp()`, прозрачность теперь сохраняется (альфа-канал), а не сплющивается на белый фон — WebP умеет то, что не умел JPEG | ✅ |
| 4 | Оба чат-контроллера (виджет + админка) сохраняют `.webp` вместо `.jpg` | ✅ |
| 5 | Каталог (обложка + галерея, `useImageCompression.ts`): `browser-image-compression` теперь выдаёт `image/webp`; уже-webp файлы меньше целевого размера не трогаем повторно, всё остальное конвертируем даже если по весу укладывается — иначе на диске была бы смесь форматов | ✅ |

| 7 | Проверено вживую через реальный `POST /api/admin/chat/image` на проде: ответ — валидный `.webp`, 1024px, 20 КБ, без артефактов на тексте | ✅ |

## 🔜 Хранение изображений — политика ретеншна и настройки в админке — идея на будущее

> Запрошено 2026-08-24 вместе с переходом на WebP выше, но это отдельная, более
> крупная задача — пока не начато, зафиксирована идея и то, что успел прояснить.

**Предложение автора:** хранить картинки 1 неделю с момента загрузки, чистить
кроном; картинки, привязанные к открытому спору/диспуту по возврату, не удалять
пока спор не закрыт; плюс переключатель в админке «оригинал / лимит по весу».

**Что важно понять до реализации:**

| # | Что | Пояснение |
|---|---|---|
| 1 | Недельное правило нельзя вешать на ВСЕ картинки | Сейчас `StorageCleanup.php` чистит по ссылкам (нет ссылки в БД → удаляется через час), а не по возрасту — фото товара, лого, аватарки живут, пока жива запись, которая на них ссылается (месяцами/годами). Правило «неделя и под нож» их бы снесло |
| 2 | «Спор/диспут» физически не с чем сверять | Возвраты (см. раздел выше, «🔜 Возвраты товаров») не реализованы вообще — нет ни таблицы, ни статуса спора. Чат же вообще не привязан к заказу (`chat_threads` — только магазин+покупатель), так что фото из чата не может «знать» про спор в принципе |
| 3 | Вывод: недельный ретеншн + исключение для спора — это на самом деле политика для будущих фото-доказательств возврата (пункт В6 выше, «приложить фото (для брака)»), а не общая политика по всем картинкам сайта. Строить крон с проверкой статуса спора раньше самой таблицы возвратов — гадать вслепую | Делать вместе с фичей возвратов (В1–В7), не раньше |
| 4 | Единицы на бегунке — КБ, не МБ | В диктовке названо «100/200/500 мегабайт» — явно опечатка, для изображений это КБ. Конкретные тиры лучше выбрать после того, как накопится статистика по реальным фото в WebP (тот же лимит КБ в WebP даёт заметно лучшую картинку, чем в JPEG — старые тиры могут оказаться избыточно щедрыми) |
| 5 | Глобально или per-shop | Per-shop — платформа мультитенантная, и это укладывается в уже существующий паттерн (например `chat_customer_delete_enabled` в настройках магазина) |
| 6 | Связь картинка ↔ спор | Не эвристика — как только появится таблица заявок на возврат (В1), это будет прямой внешний ключ с фото-доказательством на неё; крон просто джойнит и смотрит статус |
| 7 | Grace-период после закрытия спора | По умолчанию отдельный не нужен — картинка просто перестаёт быть «защищённой» и попадает под обычную очистку на следующий проход крона. Если беспокоит повторное открытие спора — можно добавить небольшой буфер (например +48ч), но это опция на потом, не обязательное решение |

**Что из этого можно делать уже сейчас, не дожидаясь возвратов:** переключатель
«оригинал / лимит по весу» для сжатия КАТАЛОГА (это по сути настройка порогов
`useImageCompression.ts`, которые сейчас зашиты в коде — 1 МБ/1920px обложка,
200 КБ/1280px галерея) — сделать его per-shop toggle в настройках магазина, по
образцу уже существующих. Недельный ретеншн + исключение для спора — ждёт фичи
возвратов.

## 🔜 Возвраты товаров (и доставки) — идея на будущее

> Запрошено 2026-08-21: «возвраты будут, от этого никуда не денешься». Сходил в
> интернет (закон РФ «О защите прав потребителей», практика Wildberries/Ozon,
> документация ЮKassa) и проверил, что уже есть в коде.

**Что есть сейчас:** ничего. `OrderController::updateStatus` при отмене заказа
возвращает товар на склад и обнуляет комиссию шопера — но **деньги покупателю не
возвращаются**, это не автоматизировано вообще. У `YooKassaService` есть только
`createPayment()`, метода возврата нет. Вебхук (`PaymentController::
handleYooKassaWebhook`) обрабатывает только `payment.succeeded` — всё остальные
события (в т.ч. `refund.succeeded`) сейчас молча игнорируются.

**Юридический минимум (закон РФ, дистанционная торговля):**

| Что | Правило |
|---|---|
| Право на возврат без объяснения причины | 7 дней с момента передачи товара (кроме товара, сделанного под заказ) |
| Срок возврата денег | 10 дней с момента, когда покупатель потребовал возврат |
| Доставка ОБРАТНО (от покупателя), товар надлежащего качества | Оплачивает покупатель |
| Доставка ОБРАТНО, товар с браком/не тот | Оплачивает продавец (компенсирует) |
| Первоначальная доставка (та, что уже была), товар надлежащего качества | **Не возвращается** — это оказанная услуга |
| Первоначальная доставка, брак/вина продавца | Возвращается вместе с товаром — это ущерб потребителя |

Ключевой вывод: **доставку нельзя возвращать по одному правилу для всех возвратов** —
нужно различать причину (брак / просто передумал), это разные суммы к возврату.

**Что потребуется, если решим делать:**

| # | Что |
|---|---|
| В1 | Таблица `order_returns` в схеме шопа: `order_id`, статус (`requested` → `approved`/`rejected` → `received` → `refunded`), причина, тип причины (`defect` / `changed_mind`), какие позиции и в каком количестве (частичный возврат заказа — не всегда весь заказ целиком) |
| В2 | `YooKassaService::refund()` — сейчас нет вообще. Возврат делается по `payment_id` заказа, полный или частичный (частичные разрешены, минимум 1₽) |
| В3 | Сумма возврата = логика из таблицы выше (В1) — считать по типу причины, не всегда «сумма заказа минус ничего» |
| В4 | Вебхук: добавить обработку `refund.succeeded`/`refund.canceled`, чтобы не полагаться только на синхронный ответ API — подтверждать возврат по факту |
| В5 | Admin UI: список заявок на возврат, кнопка «одобрить» → пересчитанная сумма → «вернуть деньги» |
| В6 | Мобилка/виджет: экран «Заявка на возврат» у покупателя — выбрать позиции, причину, приложить фото (для брака) |
| В7 | Ограничение ЮKassa: возврат только если платёж в статусе `succeeded`. **Обновление 2026-09-01:** больше не всегда так просто — с Режимом C (см. «По весу — перевзвешивание» ниже) `YooKassaService::createPayment()` умеет и холд (`capture: false`), не только `succeeded`-платежи с ходу. Для заказа с висящим холдом (`waiting_for_capture`, ещё не взвешен) возврат в обычном смысле неприменим — там нужна отмена холда (`cancelPayment()`, уже есть), не `refund()`. Реализуя возвраты, нужно различать: обычный `succeeded`-платёж → `refund()`; висящий холд → `cancelPayment()`; уже захваченный + отдельно оплаченная доплата → возможно два отдельных возврата |
| В8 | Фото-доказательства из В6 — ретеншн: хранить 1 неделю с момента загрузки, чистить кроном, НО не удалять пока связанная заявка на возврат не в терминальном статусе (`refunded`/`rejected`). Подробности и открытые вопросы — см. раздел «🔜 Хранение изображений — политика ретеншна» выше |

**Статус:** идея зафиксирована, не начато. Открытые вопросы: разделяем ли причины
возврата (брак vs передумал) с самого начала, или на первом шаге — только брак (это
единственный случай, где шопер вообще обязан оплачивать обратную доставку); нужен
ли покупателю отдельный экран заявки на возврат или пока это делается вручную
(шопер сам создаёт возврат в админке по звонку/сообщению покупателя).
