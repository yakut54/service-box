# ServiceBox — Plan

## ⚠️ Правила работы с миграциями

**Миграционных файлов быть не должно.** Порядок работы с любым изменением схемы БД:

1. Создать миграцию → применить на сервере (`php artisan migrate`)
2. Проверить что всё работает
3. Внести изменения в `database/schema/pgsql-schema.sql`
4. **Удалить файл миграции нахуй**

Файлы миграций — мусор. Из-за них происходят несоответствия между схемой и реальной БД.

## Стек

- **Backend:** Laravel 11, PostgreSQL 16 (multi-tenant schemas), Redis, Sanctum
- **Frontend:** Vue 3 + TypeScript, Tailwind CSS (admin), Pinia, Vite
- **Infrastructure:** Docker, Nginx, GitHub Actions (deploy on push to `flutter-app`)
- **Server:** root@193.168.49.102, app `/var/www/servicebox/`, домен `https://yakut54.ru`
- **Queue driver:** `sync` (нет async-очередей — все операции синхронные)

## Архитектура

```
servicebox/
├── app/              — Laravel API
├── admin/            — SPA для владельца магазина (Vue 3)
├── widget/           — Встраиваемый виджет для сайта клиента (Vue 3, Shadow DOM)
└── database/         — schema/pgsql-schema.sql (единственный источник истины по схеме БД)
```

Каждый магазин — отдельная PostgreSQL-схема `shop_{id}`. Таблицы `customers`, `products`, `orders`, `bookings`, `masters` и др. изолированы per-tenant.

### ⚡ Закон синхронизации — обязателен для каждого этапа

**Любое действие в любом из трёх каналов (TG / MAX / сайт) должно немедленно отразиться во всех трёх.**

| Действие | TG бот | MAX бот | Сайт (автополлинг) |
|---|---|---|---|
| Клиент оставил оценку | Шопер + мастер уведомлены | Шопер + мастер уведомлены | Отзыв появился в ReviewsView |
| Клиент перенёс запись | Кнопки убраны, шопер + мастер уведомлены | Кнопки убраны, шопер + мастер уведомлены | Запись = cancelled в BookingsView |
| Шопер отправил win-back | Клиент получил (если есть TG) | Клиент получил (если есть MAX) | — (нет нужды) |
| Клиент записался после win-back | Шопер + мастер уведомлены | Шопер + мастер уведомлены | Новая запись в BookingsView |

**Следствия:**
- Если действие произошло в TG → кнопки в MAX тоже убираются (`removeButtons`)
- Если действие произошло в MAX → клавиатура в TG тоже убирается (`removeKeyboard`)
- Уведомления шоперу/мастеру всегда уходят в **оба** бота независимо от канала-источника
- Состояние в DB всегда первично — сайт читает из DB, боты пишут в DB

Точка вставки: `handleRatingCallback` в `TelegramController` и `MaxController` — после успешного `INSERT INTO reviews`.

### Серия П — Перенос записи из бота

> Клиент не может прийти — вместо отмены переносит.
> Сейчас: только кнопка «Отменить». Отменённая запись — потеря выручки шопера.
> Цель: кнопка «📅 Перенести» → бот отменяет запись + отправляет ссылку на виджет с prefill → клиент выбирает новое время.

#### Архитектура

- Кнопка добавляется **только в 24h напоминание** (в 2h — слишком поздно переносить)
- Точка: `TelegramService::notifyBookingReminder` и `MaxService::notifyBookingReminder` при `$type === '24h'`
- При нажатии: `status = cancelled` + специальный текст уведомлений «перенёс» (не «отменил»)
- Ссылка виджета: `https://yakut54.ru/book/{apiKey}?service_id={id}` — клиент выбирает время заново
- **Синхронизация**: booking в DB → `cancelled` → автополлинг в `BookingsView` подхватит → шопер/мастер уведомлены в Telegram + MAX

## 📱 Мобильное приложение — Флот Шоперов (white-label)

> **Пивот 2026-08-18.** Было: одно универсальное APK для всех байеров всех шоперов, с
> онбордингом/сканером QR/переключателем магазинов внутри приложения. Стало: у каждого
> шопера — своё отдельное APK, байер вообще не выбирает магазин, приложение с рождения
> знает только про своего шопера.
>
> **Причина:** шоперы не должны видеть и знать друг о друге (~10 шоперов запланировано,
> ни один не в курсе про остальных). Конкуренты в нише (Altegio, DIKIDI) уже продают ровно
> такую white-label модель как платную фичу — рынок подтверждён.
>
> **Только физические товары в MVP.** Услуги (`products_service`/bookings) и цифровые товары
> (`products_digital`) уже поддержаны в БД и никуда не делись — но НЕ показываются в новом
> мобильном приложении. Включаются точечно через entitlements, когда конкретный шопер за
> это платит — без единой правки кода на момент включения.
>
> Полная концепция и обоснование (архитектура, феча-флаги, дистрибуция, CI/CD) — артефакт
> «Флот Шоперов», опубликован в чате 2026-08-18.

### Архитектура

- **Один APK = один шопер.** `shop_code` (по факту — `api_key` магазина) зашивается на
  этапе сборки через Flutter **flavors** + `--dart-define`, не выбирается в рантайме.
- У каждого флейвора свой `applicationId`, имя, иконка — иначе Android не даст поставить
  наши же приложения рядом на одном телефоне.
- **Бэкенд не меняется концептуально** — приложение ходит в те же `widget/*` эндпоинты,
  что и сейчас веб-виджет, с уже зашитым `X-Shop-ID`. Отдельный `GET /app/{shop_code}` для
  рантайм-обнаружения магазина (старый М0.1/М0.2) **не нужен** — код магазина не вводится
  пользователем, он уже в сборке.
- **Entitlements** — новая таблица `shop_features (shop_id, feature_key, enabled)`. Гейтит
  booking/digital-goods и на бэкенде (что отдаёт API), и в приложении (какой UI показывать).
  Дефолт — все флаги `false`, кроме физ-товаров. Реальных шоперов в проде нет и не было
  никогда (см. `shop_omtgfybbrig5` — это тестовые данные), поэтому миграционная осторожность
  не нужна, дефолты можно менять свободно.
- **Dark launch:** код новой фичи (в т.ч. UI-экраны) катится во **все** флейворы сразу,
  выключенным флагом — включается позже щелчком в мастер-админке, без новой сборки/заливки
  в RuStore. Пересборка нужна только один раз — когда код фичи впервые попадает в приложение.
- **Дистрибуция — RuStore** (не Google Play; iOS пока не рассматриваем). CI/CD: GitHub
  Actions собирает APK матрицей по флейворам → заливает через RuStore Publisher API. Первая
  версия каждого нового шопера в RuStore — вручную через консоль (автоматизируются только
  последующие обновления).

#### М5 — Яндекс.Доставка

> **Базовый URL:** `https://b2b.taxi.yandex.net`
> **Авторизация:** `Authorization: Bearer <token>` (токен из личного кабинета Яндекс.Доставки)
> **Демо/песочница:** в официальной документации не найдена — под вопросом, уточняем у поддержки Яндекса
> **Токен API:** выдаётся в личном кабинете dostavka.yandex.ru через вкладку «Интеграции» → «Получить токен». У пользователя эта вкладка не отображается — написали в поддержку Яндекса, ждём ответ
> **Договор:** нужен для продакшена — регистрация на dostavka.yandex.ru

**Ключевые эндпоинты Яндекс API:**
- `POST /b2b/cargo/integration/v2/offers/calculate` — расчёт стоимости доставки
- `POST /b2b/cargo/integration/v2/claims/create` — создать заявку на курьера
- `POST /b2b/cargo/integration/v2/claims/accept` — подтвердить заявку (курьер едет)
- `GET /b2b/cargo/integration/v2/claims/info?claim_id=` — трекинг статуса

**Что нужно для расчёта стоимости:**
- Координаты точки A (адрес магазина/склада)
- Координаты точки B (адрес клиента)
- Вес и габариты товаров (опционально — для точной цены)

**Архитектура интеграции:**
```
Клиент вводит адрес →
  Мобилка: POST /mobile/delivery/estimate {address} →
    Бекенд: запрос к Яндекс API /offers/calculate →
      Вернуть стоимость клиенту →
        Если order.total >= free_delivery_from → доставка за счёт магазина →
          Клиент оплачивает заказ →
            Бекенд: POST /claims/create → POST /claims/accept → курьер назначен
```

## 🔜 Развесной товар (единицы измерения) — идея на будущее

> Возникло при наполнении товаров магазина «Барбариска» (2026-08-18): овощи/фрукты
> сейчас заведены как фасовка фиксированного веса (пакет ~1кг/~500г — отдельная позиция
> товара, покупают целым количеством пакетов). Это рабочий вариант, но не настоящая
> «развесная» продажа как в Wildberries/Ozon/Яндекс Лавка, где покупатель сам выбирает
> граммовку.

**Почему не сделано сразу:** система сейчас везде считает count товара, а не вес —
`order_items.quantity` целое число, цена = цена за товар целиком (не за кг). Настоящий
развес — это отдельная фича, трогает корзину, чекаут, оплату, витрину и мобилку
одновременно, не пара строк.

**Что потребуется, если решим делать:**

| # | Что |
|---|---|
| Р1 | `products.unit` — единица измерения (`pcs` / `kg` / `g` / `l`) |
| Р2 | `products.price` меняет смысл на «цена за unit» (за кг) вместо «цена за товар» — там где `unit != pcs` |
| Р3 | `products.step` — минимальный шаг выбора веса (например, 50г) |
| Р4 | `order_items.quantity`: `INTEGER` → `NUMERIC`, чтобы хранить дробный вес |
| Р5 | Виджет/мобилка: степпер выбора веса вместо кнопок +/- на развесных товарах |
| Р6 | Пересчёт суммы заказа после фактической сборки (заявленный вес ≠ реальный) — доплата/возврат через YooKassa |
| Р7 | Admin UI: поле "фактический вес" при сборке заказа продавцом |

**Статус:** идея зафиксирована, не начато. Ждём решения — нужна ли вообще (зависит от
того, появятся ли шоперы, которым принципиально важна развесная торговля).
