# ServiceBox — Чат «Шопер ↔ Байер»

Чат между владельцем/сотрудниками магазина и покупателями — интерфейс по
мотивам Telegram, работает и в админке (веб), и в мобильном приложении.
Ниже — архитектура, схема БД, API, поведение доставки сообщений, интерфейс
на обеих сторонах и статус реализации.

**Текущий статус: реализовано полностью, кроме режима множественного выбора
сообщений (см. §7.8). В проде, проверено вживую реальным пользователем.**

Ключевые решения:

| Развилка | Решение |
|---|---|
| Доставка сообщений | WebSocket (Laravel Reverb) как основной путь, polling — редкая подстраховка на 20 сек на случай обрыва сокета. Изначально был только polling, Reverb добавлен позже — см. §4 |
| Структура чата | Один диалог на покупателя (как переписка в Telegram) — не отдельный чат на каждый заказ |
| Кто отвечает от магазина | Владелец + администраторы. Мастера не участвуют — не их зона ответственности |
| Вложения | Только фото в v1. Файлы произвольного типа — см. «Файлы» в конце документа |
| Кто пишет первым | Покупатель — магазин не может «постучаться» первым (защита от спам-рассылок через чат) |

---

## 0. Что уже есть в проекте и на что это опирается

- **Мультитенантность**: у каждого магазина своя PostgreSQL-схема (`shop_{id}`). Все
  таблицы чата — per-tenant, как `customers`, `orders`, `products`.
- **Покупатель уже умеет логиниться**: `customer_sessions` (60 дней, мобильное
  приложение) и краткий `phone-token` (30 мин, веб-виджет) — см.
  `VerifyPhoneSession` / `VerifyPhoneToken`. Чат в мобильном приложении опирается
  на уже существующую сессию покупателя. Веб-виджет чат пока не получил — см.
  «Другие возможные доработки».
- **Роли на стороне магазина**: `ShopStaff.role` (`owner` / `admin` / `master`),
  см. `SetShopFromAuth`. Чат доступен `owner` и `admin`, не `master`.
- **Загрузка изображений**: `Storage::disk('public')`, тот же диск, что и у
  остальных фото в проекте.
- **StorageCleanup — критично**: ночной крон удаляет любой файл в `uploads/`,
  если его URL не встречается ни в одной из отслеживаемых колонок БД.
  `chat_messages.image_url` добавлен в `StorageCleanup::collectUsedPaths()` —
  этот же класс бага уже дважды стоил целого дня разбирательств с другими
  колонками, здесь исправлено сразу.
- **Правило тенантных миграций**: миграция создаётся, применяется, проверяется,
  переносится в `database/schema/pgsql-schema.sql`, файл миграции удаляется —
  всё одним коммитом. Ниже сразу дана итоговая схема, отдельных миграционных
  файлов в репозитории для чата нет.

## 1. Модель данных

Обе таблицы — в **каждой tenant-схеме** (рядом с `customers`, `orders` и т.д.
в `create_shop_schema()`):

```sql
-- chat_threads — один диалог = один покупатель этого магазина
CREATE TABLE %I.chat_threads (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id           UUID NOT NULL REFERENCES %I.customers(id) ON DELETE CASCADE,
    last_message_at       TIMESTAMPTZ,
    last_message_preview  TEXT,               -- первые ~80 символов последнего сообщения, для списка диалогов без JOIN
    unread_by_shop        INTEGER NOT NULL DEFAULT 0,
    unread_by_customer    INTEGER NOT NULL DEFAULT 0,
    shop_last_read_at     TIMESTAMPTZ,        -- informational, НЕ источник статуса сообщения (см. §1.1)
    customer_last_read_at TIMESTAMPTZ,
    is_blocked_by_shop    BOOLEAN NOT NULL DEFAULT FALSE, -- магазин закрыл диалог (спам/абьюз), см. §6
    created_at            TIMESTAMPTZ DEFAULT NOW(),
    updated_at            TIMESTAMPTZ DEFAULT NOW()
);
CREATE UNIQUE INDEX ON %I.chat_threads(customer_id);  -- ровно один диалог на покупателя
CREATE INDEX ON %I.chat_threads(last_message_at DESC);

-- chat_messages — сообщения внутри диалога
CREATE TABLE %I.chat_messages (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    thread_id            UUID NOT NULL REFERENCES %I.chat_threads(id) ON DELETE CASCADE,
    sender_type          TEXT NOT NULL CHECK (sender_type IN ('shop', 'customer')),
    sender_staff_id      UUID REFERENCES public.shop_staff(id) ON DELETE SET NULL, -- null для owner и для sender_type='customer'
    client_message_id    UUID,               -- см. §5.1 (защита от дублей при retry)
    body                 TEXT,               -- до 2000 символов, может быть NULL если только фото
    image_url            TEXT,
    status               TEXT NOT NULL DEFAULT 'sent' CHECK (status IN ('sent', 'read')), -- единственный источник правды, см. §1.1
    reply_to_message_id  UUID REFERENCES %I.chat_messages(id) ON DELETE SET NULL, -- см. §7.3
    edited_at            TIMESTAMPTZ,        -- см. §7.4
    created_at           TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX ON %I.chat_messages(thread_id, created_at);
CREATE UNIQUE INDEX ON %I.chat_messages(thread_id, client_message_id)
    WHERE client_message_id IS NOT NULL;

ALTER TABLE %I.chat_messages ADD CONSTRAINT chat_messages_not_empty
    CHECK (body IS NOT NULL OR image_url IS NOT NULL);
```

В `public.shops` — `chat_customer_delete_enabled BOOLEAN DEFAULT FALSE NOT NULL`
(см. §7.5).

**Почему `sender_staff_id` ссылается на `public.shop_staff`, а не на tenant-таблицу**:
`shop_staff` — `public`-схема (единая на все магазины), как `shops` и
`masters`-приглашения — та же связь, что у `masters.user_id → public.users`.

**Почему `last_message_preview`/`unread_*` денормализованы, а не считаются на
лету** — список диалогов (потенциально сотни покупателей) открывается одним
запросом без `COUNT()`/`MAX()` по всем сообщениям. Обновляются атомарно в той
же транзакции, что создаёт сообщение.

### 1.1 Статус прочтения — единственный источник правды

- **`chat_messages.status`** — единственный источник правды, прочитано ли
  КОНКРЕТНОЕ сообщение. Клиент смотрит только на это поле.
- `/read` — один массовый `UPDATE ... SET status = 'read' WHERE thread_id = ? AND sender_type = <чужая сторона> AND status = 'sent'`, не по одному сообщению.
- `shop_last_read_at`/`customer_last_read_at` — только вспомогательная метка
  времени, не используется для статуса отдельного сообщения.
- `unread_by_shop`/`unread_by_customer` меняются только атомарно
  (`increment()`/`decrement()` или `... = ... + 1`), никогда через
  read-modify-write в PHP.
- Статус прочтения виден **обеим сторонам симметрично** (как в настоящем
  Telegram, не как в B2B-чатах поддержки Intercom/Crisp, которые прячут его
  специально) — покупатель не должен быть человеком второго сорта в
  собственном диалоге с магазином.
- Без промежуточного «доставлено» — статус, завязанный на факт опроса,
  был бы фикцией (опрос мог случиться на любом экране, не обязательно в
  чате). Только `sent`/`read`.

### 1.2 Переиспользование номеров телефона — известный системный риск

Не специфично для чата: покупатель идентифицируется по номеру телефона, а
операторы переиспользуют номера после периода неактива. Новый владелец
номера унаследует всю историю прежнего — заказы, адреса, и теперь ещё
переписку с фото. Чат ощутимо повышает ставки (личная переписка чувствительнее
списка товаров), но это системное допущение всего проекта, не решается в
рамках чата. Возможное направление на будущее — периодическая анонимизация
давно неактивных покупателей, см. «Другие возможные доработки».

## 2. Кто может писать первым

**Покупатель пишет первым**, диалог создаётся при первом сообщении от
покупателя (`POST /widget/chat/messages`, `INSERT ... ON CONFLICT (customer_id)
DO UPDATE` — не голый `firstOrCreate`, который не атомарен при двойном
тапе/retry и упёрся бы в уникальный индекс). Магазин отвечает в уже
существующий тред — `404`, если покупатель ни разу не писал. Это защита от
спам-рассылок через чат под видом личного диалога (у магазина уже есть
Telegram/MAX-уведомления для массовых сообщений).

## 3. API

### 3.1 Мобильное приложение (покупатель) — `/widget/chat/*`

Только мобильное приложение, не веб-виджет — у мобильного приложения сессия
живёт 60 дней (`X-Phone-Session`), у виджета — 30 минут (`VerifyPhoneToken`),
непригодно для чата. Throttle — именованные лимитеры по `X-Phone-Session`,
не по IP (см. §3.2): `chat-read` (60/мин: `GET /chat`, `POST /chat/read`,
`GET /chat/poll`, `POST /chat/broadcasting-auth`), `chat-write` (20/мин:
`POST /chat/messages`, `DELETE /chat/messages/{id}`), `chat-image` (10/мин:
`POST /chat/image`).

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/widget/chat` | Диалог покупателя: сообщения (`?before=`, курсор — см. §3.3), `thread.id`, `is_blocked_by_shop` |
| `POST` | `/widget/chat/messages` | Отправить (`body`/`image_url`, `client_message_id`, опционально `reply_to_message_id`) |
| `DELETE` | `/widget/chat/messages/{id}` | Удалить своё сообщение — только если `shops.chat_customer_delete_enabled` включён (см. §7.5) |
| `POST` | `/widget/chat/read` | Отметить диалог прочитанным |
| `GET` | `/widget/chat/poll` | `{has_new, unread_total, shop_read_up_to}` — подстраховка поверх WebSocket, см. §4 |
| `POST` | `/widget/chat/image` | Загрузить фото (без svg/gif, сервер сжимает до ≤100 КБ — см. §5) |
| `POST` | `/widget/chat/broadcasting-auth` | Ручная авторизация приватного WS-канала — покупатель не Sanctum-пользователь, см. §4 |

### 3.2 Админка (владелец/администратор) — `/admin/chat/*`

Под `auth:sanctum` + `auth.shop` + `not.master`. Именованные лимитеры по
`user()->id`: `chat-admin-read` (180/мин), `chat-admin-write` (30/мин),
`chat-admin-moderate` (30/мин), `chat-admin-image` (10/мин). Изначально здесь
стоял голый `throttle:N,1` на каждый роут — баг, найденный вживую: для
авторизованного пользователя такой лимитер строит ключ **только из
`sha1(user_id)`, без роута**, поэтому все 8 роутов делили один общий счётчик,
и активный polling блокировал отправку сообщений.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/admin/chat/threads` | Список диалогов, сортировка по свежести, поиск по имени/телефону |
| `GET` | `/admin/chat/threads/{id}/messages` | Сообщения (`?before=`), контекст покупателя (`total_orders`/`total_spent`) |
| `POST` | `/admin/chat/threads/{id}/messages` | Ответить, опционально `reply_to_message_id` |
| `PATCH` | `/admin/chat/threads/{id}/messages/{id}` | Редактировать своё сообщение (только текст) — см. §7.4 |
| `DELETE` | `/admin/chat/threads/{id}/messages/{id}` | Удалить любое сообщение (модерация), чистит файл с диска |
| `POST` | `/admin/chat/threads/{id}/read` | Отметить прочитанным |
| `POST` | `/admin/chat/threads/{id}/block` | Заблокировать/разблокировать переписку — см. §6 |
| `GET` | `/admin/chat/poll` | `{unread_by_thread, total_unread}` — один запрос на всю админку |
| `POST` | `/admin/chat/image` | Загрузить фото |

Кто из сотрудников написал — `sender_staff_id` (`null` у владельца — у него
нет записи `ShopStaff`). Покупателю имя конкретного сотрудника не показывается
— наружу это «магазин ответил», не «Оля ответила».

### 3.3 Курсоры пагинации — по времени, не по ID

`id` — `gen_random_uuid()`, не сортируется по времени. Клиент передаёт
`?before=<message_id>`, сервер резолвит его в `(created_at, id)` и сравнивает
`WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 30`
— пара, не только `created_at`, на случай двух сообщений с одинаковым
timestamp. Невалидный UUID в `before`/`after` — явный `422`, не сырая ошибка
Postgres.

## 4. Доставка сообщений — WebSocket + polling-подстраховка

Основной путь — **Laravel Reverb** (self-hosted, Pusher-совместимый,
бесплатный, отдельный контейнер `reverb` в `docker-compose.prod.yml`, порт
6001; host nginx проксирует `/app/` с `Upgrade`/`Connection` заголовками).
Событие `ChatMessageBroadcast` (`message.new` / `message.updated` /
`message.deleted` / `thread.read` / `thread.blocked`) летит на приватный
канал `chat.thread.{shopApiKey}.{threadId}`.

- **Авторизация канала — два разных пути**, потому что у сотрудника и
  покупателя разная авторизация целиком:
  - Сотрудник — обычный Sanctum, стандартный `/api/broadcasting/auth` +
    `routes/channels.php` (`Broadcast::channel('chat.thread.{shopApiKey}.{threadId}', ...)`,
    проверяет, что пользователь — владелец или admin именно этого магазина).
  - Покупатель — не Sanctum-пользователь (`X-Phone-Session`, не guard),
    стандартный broadcasting-auth ему не подходит. Свой
    `POST /widget/chat/broadcasting-auth`: проверяет, что запрошенный канал —
    ровно канал СВОЕГО треда, и вручную подписывает через `Pusher\Pusher`
    (пакет уже тянется зависимостью Reverb, готовый `socket_auth()`).
- **И админка (`laravel-echo`+`pusher-js`), и мобильное приложение** (свой
  минимальный клиент Pusher-протокола поверх `web_socket_channel`, без
  нативных SDK — см. `mobile/lib/data/chat_realtime_client.dart`) на любое
  событие просто **перезапрашивают то же окно сообщений**, что и раньше при
  обычном poll — одна и та же логика слияния/удаления на оба транспорта, не
  дублируется.
- **Polling остался как подстраховка** на случай обрыва сокета/пропущенного
  события при реконнекте — 20 сек в открытом диалоге (было 3-4 сек, когда
  polling был единственным путём), плюс список диалогов и бейдж непрочитанных
  опрашиваются отдельно (10-15 сек), для случаев, когда WebSocket ещё не
  подключился.
- Отправка сообщения — обычный HTTP-запрос, не через WS; оптимистичное
  обновление UI (сообщение сразу в ленте), `client_message_id` делает повтор
  после сетевой ошибки идемпотентным (см. §5.1).

Изначально в проекте не было ни Redis, ни очередей, ни broadcasting —
оценивалось на 4-7 рабочих дней, в итоге реализовано и вживую
проверено за одну ночь.

## 5. Фото в сообщениях

1. Клиент выбирает фото/делает снимок (неважно, какого размера файл) →
   **сжимается на клиенте** перед отправкой до ~100 КБ / ~1024px —
   экономия трафика, не гарантия результата. Веб (админка) —
   `compressIfNeeded` (та же функция, что и у товарных фото). Мобильное —
   `compressImageBytes()` (`core/image_compress.dart`, isolate + пакет
   `image` — уже существовала в проекте для аватаров, отдельный пакет
   `flutter_image_compress` не понадобился).
2. `POST /widget|admin/chat/image` — **никакой проверки размера файла и
   никакого сообщения пользователю про размер**. Каким бы огромным ни был
   исходник — сервер сам гарантированно пересжимает его до ≤100 КБ через
   `ImageCompressionService` (GD: decode → resize ≤1024px → JPEG со
   ступенчато падающим качеством), а не отклоняет с ошибкой. Единственный
   потолок — общий лимит PHP на входящий запрос (25/30 МБ в Dockerfile,
   `client_max_body_size 15M` на nginx) — инфраструктурная защита от DoS, не
   бизнес-правило, которое видит пользователь. Проверено вживую: 36 МБ шумной
   синтетики → 63 КБ за 0.58с; реальный JPEG 1.5 МБ → 86 КБ.
3. Разрешены только `jpeg`/`png`/`webp` — **без svg** (валидация `image` по
   умолчанию включает svg, а SVG от постороннего покупателя, которое откроет
   сотрудник в браузере, может нести `<script>`; правило должно быть именно
   `mimes:jpeg,png,webp`, не `image:...` — у `image` в Laravel параметров нет,
   всё после двоеточия молча игнорируется, залитый `.svg` со `<script>`
   проходил валидацию, пока это не нашли живым тестом) и **без gif** (ни
   `browser-image-compression`, ни то, что доступно на мобильном, не сжимают
   GIF с сохранением анимации — честно сжать нечем, поэтому не принимаем).
4. Открытие фото на весь экран — переиспользует тот же модальный просмотр,
   что уже используется в галерее товара.

### 5.1 Защита от дублей при повторной отправке

Клиент сам генерирует `client_message_id` (UUID) один раз при формировании
сообщения и передаёт его при каждой попытке `POST /messages`, включая
повторы после обрыва связи. Уникальный индекс
`chat_messages(thread_id, client_message_id)` + `ON CONFLICT` — повтор с тем
же `client_message_id` возвращает уже существующее сообщение, не создаёт
дубль и не считается ошибкой.

### 5.2 Удаление сообщения — файл должен удаляться из хранилища

- **Модерация магазином** (`DELETE /admin/.../messages/{id}`) — жёсткое
  удаление (не пометка «удалено» — это не «я передумал» у отправителя, а
  «магазин убрал неприемлемый контент»), обязательно вызывает
  `StorageService::deleteByUrl($message->image_url)`, если было фото — тот
  же класс бага, что уже дважды ловили на `StorageCleanup` (БД забыла про
  файл → файл висит на диске мёртвым грузом навсегда), только в обратную
  сторону.
- **Покупатель может удалить только своё сообщение**, и только если магазин
  включил `shops.chat_customer_delete_enabled` в Настройках (выключено по
  умолчанию) — см. §7.5. Сообщение магазина покупателю недоступно для
  удаления ни при каких настройках.
- Оба пути шлют `message.deleted` в реальном времени (см. §4) — собеседник
  видит исчезновение сообщения без перезахода в чат.

## 6. Модерация и защита от абьюза

- **Rate limit на отправку** — см. §3.1/§3.2.
- **Блокировка диалога магазином** — `is_blocked_by_shop`, кнопка в шапке
  диалога. После блокировки `POST /widget/chat/messages` отвечает `403`
  («Магазин ограничил переписку»). История переписки остаётся читаемой —
  блокируется только отправка нового, не факт существования диалога.
  Разблокировка — та же кнопка.
- Чат не влияет на оплату/статусы заказа — это чисто переписка, не канал для
  «прислать поддельный чек».

## 7. Взаимодействия с сообщениями — ответ, редактирование, удаление, звук

По мотивам Telegram/WhatsApp — но не один в один: там, где поведение
референса не подошло, ниже explicitly указано, что сделано иначе и почему.

### 7.1 Быстрые действия — платформенные различия

- **Мобильное**: долгое нажатие на пузыре → нижнее меню
  Ответить/Скопировать/Удалить (Удалить — только на своих сообщениях).
  Свайп **влево** на пузыре = быстрый ответ (частичный драг с пружинным
  возвратом, иконка ответа проявляется у правого края) — направление
  специально сделано влево, не вправо: на **своих** сообщениях (справа,
  часто короткие) вправо было неудобно тянуть, места не хватало. Каждый
  пузырь — минимум 50% ширины экрана (не только максимум 75%), чтобы всегда
  было где ухватиться для свайпа вне зависимости от длины текста.
- **Админка (десктоп)**: свайпа на десктопе не бывает ни в одном настольном
  мессенджере (тянуть мышью уже занято под выделение текста) — вместо этого
  hover-иконки на пузыре (Ответить/Редактировать[своё]/Удалить), появляются
  при наведении курсора — тот же принцип, что в Telegram Desktop.
- **Полноценный режим множественного выбора с чекбоксами** (как на
  референс-скриншоте WhatsApp — верхняя панель «Выбрано N», массовое
  Копировать/Удалить) — **не реализован**, сознательно отложен: точечные
  действия на одном сообщении уже покрывают Ответить/Скопировать/
  Редактировать/Удалить, чекбоксы поверх этого — отдельная следующая
  итерация, backend для неё (reply/edit/delete endpoints) уже готов.
- **«Переслать» не реализован**: в этом проекте один диалог = один
  покупатель, переслать было бы физически некуда (нет второго треда).

### 7.2 Реалтайм-обновление ленты

И на мобильном, и в админке любое WS-событие (или очередной poll-тик)
переспрашивает окно из ~30 последних сообщений и делает три вещи разом:
добавляет новые, обновляет статусы/правки у уже показанных, и убирает те,
что пропали с сервера (модерация) — иначе удалённое сообщение зависало бы в
уже открытом чате навсегда, раз обновление умело только добавлять (реальный
баг, найденный и исправленный). Сообщения за пределами этого окна (подгружены
через «показать раньше») не трогаются.

### 7.3 Ответ на сообщение (Reply)

`chat_messages.reply_to_message_id` (`ON DELETE SET NULL` — если оригинал
потом удалили, цитата показывает «Сообщение удалено», не ломает вставку).
Реплай проверяется на принадлежность тому же треду на бэкенде — нельзя
сослаться на чужую переписку по подсмотренному UUID. Пока пишется ответ —
планка над полем ввода с превью цитаты и крестиком отмены; если оригинал —
фото, показывается его миниатюра 20×20 (иначе непонятно, на какую именно
картинку отвечают) — и в этой планке, и внутри самого отправленного
сообщения.

### 7.4 Редактирование

`chat_messages.edited_at`. Только текст (фото не редактируется — подпись это
и есть `body`, значит правка подписи уже работает через тот же endpoint).
Без ограничения по времени (как в Telegram, не 15 минут WhatsApp). Только на
стороне магазина, только своё сообщение — сравнение по `sender_staff_id`
(включая `null` у владельца, поэтому владелец правит только свои же
сообщения, не чужие — как в Telegram: даже админ группы не может
отредактировать чужой текст, только удалить). Покупателю редактирование не
дано вообще.

### 7.5 Удаление у покупателя — переключатель в Настройках

Настройки → Основное → карточка «Чат с покупателями» → тумблер «Разрешить
покупателям удалять свои сообщения» (выключен по умолчанию,
`shops.chat_customer_delete_enabled`, UI — переиспользованный `UiCheckbox`).
Покупатель может удалить только своё сообщение и только если тумблер
включён; сообщение магазина ему недоступно для удаления ни при каких
настройках.

### 7.6 Копирование

Только текст, только клиент (`navigator.clipboard.writeText` /
`Clipboard.setData`) — без изменений на бэкенде. Копирование изображения в
буфер обмена не реализовано (выигрыш сомнителен относительно сложности).

### 7.7 Звук нового сообщения

Синтезированный (не скачанный — без лицензионных рисков) двухтональный WAV,
один и тот же файл в обоих приложениях (`admin/public/sounds/chat-notify.wav`,
`mobile/assets/sounds/chat_notify.wav`). Играет только на **входящее**
сообщение и только пока чат открыт/приложение активно — push-уведомлений в
свёрнутом приложении в проекте нет вообще (см. «Другие возможные
доработки»), это отдельная большая задача. В админке есть переключатель
звука (`localStorage`, тот же принцип, что у темы).

### 7.8 Что осталось не реализовано

- Полноценный чекбоксовый режим множественного выбора (см. §7.1).
- Настоящее контекстное меню по правому клику в админке (сейчас только
  hover-иконки без общего меню) — небольшая доработка сверху готового.

## 8. Интерфейс — админка (веб, Vue)

Общий почтовый ящик (Intercom/Crisp-паттерн): двухколоночный layout — список
диалогов слева (~320px), открытый диалог справа, как в разделах
«Заказы»/«Клиенты».

- **Список диалогов** — непрочитанные жирным + бейдж-счётчик, поиск по
  имени/телефону, сортировка по свежести последнего сообщения.
- **Пункт меню «Чат»** в `AppLayout.vue` с бейджем общего числа непрочитанных
  (`useChatStore`, опрос `/admin/chat/poll`).
- **Бейдж на вкладке браузера** — `document.title` меняется, пока есть
  непрочитанные, независимо от того, какой раздел админки открыт.
- **Контекст покупателя в шапке диалога** — количество заказов и сумма
  покупок рядом с именем/телефоном.
- **Сообщения**: магазина — вправо (`primary_color` магазина), покупателя —
  влево. Группировка по дате. Галочки `✓`/`✓✓` — только на своих исходящих.
  Ответ/редактирование/удаление/звук — см. §7.
- **Пустое состояние** — «Пока никто не писал», тот же тон, что у остальных
  пустых состояний в админке.

## 9. Интерфейс — мобильное приложение (Flutter)

- **Точки входа**: иконка чата в шапке каталога (с бейджем непрочитанных,
  тот же стиль, что у иконки корзины), пункт «Чат с магазином» в профиле.
- **Экран чата**: шапка = название магазина. Пузыри — свои (покупателя)
  справа, цвет `primary_color` магазина; сообщения магазина слева, серые.
  Галочки — только на своих. `ListView` с `reverse: true`, подгрузка старых
  сообщений при скролле вверх порциями по 30.
- **Поле ввода**: текст + скрепка (фото, превью перед отправкой с крестиком
  «убрать») + кнопка отправки.
- **Оптимистичная отправка**: сообщение сразу в ленте, `client_message_id`
  делает повтор при сетевой ошибке безопасным (см. §5.1).
- Ответ/удаление/звук/свайп — см. §7.

## 🔜 Файлы — что понадобится доделать (после фото, отдельный шаг)

Файлы произвольного типа (PDF, документы, видео) сознательно не включены.
Когда возьмёмся:

| # | Что |
|---|---|
| Ф1 | `chat_messages.file_url` + `file_name` + `file_size_bytes` + `file_mime_type` — отдельные колонки, не переиспользовать `image_url` |
| Ф2 | Валидация MIME по белому списку (`pdf`, `doc(x)`, `xls(x)`, архивы) — никаких исполняемых расширений |
| Ф3 | Лимит размера файла (вероятно 10–20 МБ) |
| Ф4 | UI: иконка типа файла вместо превью, имя + размер под иконкой |
| Ф5 | Скачивание файла на мобильном — `path_provider`/`open_filex`, с проверкой разрешений |

## 🔜 Другие возможные доработки — идеи на будущее, не начато

- **Режим множественного выбора сообщений** (чекбоксы, верхняя панель
  «Выбрано N», массовое Копировать/Удалить) — см. §7.8.
- **Push-уведомления о новом сообщении, когда приложение закрыто** — в
  проекте нет ни Firebase Cloud Messaging, ни другой push-инфраструктуры
  вообще. Отдельная большая задача — FCM для Android.
- **Индикатор «печатает…»** — раньше требовал WebSocket или неприемлемо
  частого polling; теперь, когда Reverb уже есть (§4), стоимость заметно
  ниже — просто ещё одно лёгкое событие на тот же канал. Не начато.
- **Поиск по тексту сообщений** — Postgres `tsvector`, тот же принцип, что
  можно применить и к `products.name`/`description`.
- **Чат в веб-виджете** — сейчас не входит в объём, потому что у виджета нет
  долгой сессии покупателя (только 30-минутный `phone-token`).
- **Привязка сообщения к конкретному заказу** — сейчас один общий диалог без
  контекста заказа.
- **«Решено»/«Архив» для списка диалогов** — сейчас список плоский,
  сортировка по свежести. Понадобится при росте до сотен активных диалогов.
- **Переиспользование номеров телефона** — см. §1.2.
