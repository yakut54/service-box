# ServiceBox — Чат «Шопер ↔ Байер» — план разработки

> Задание от 2026-08-23: чат между владельцем/сотрудниками магазина и покупателями,
> с обменом фото (и файлами в будущем), интерфейс — по мотивам Telegram: и в
> админке (веб), и в мобильном приложении. Ниже — детальный план: архитектура,
> схема БД, API, поведение доставки сообщений, интерфейс на обеих сторонах,
> порядок реализации.

Решения, принятые до начала проектирования (все — по рекомендованному варианту):

| Развилка | Решение |
|---|---|
| Доставка сообщений | Опрос сервера (polling), не WebSocket — на сервере пока нет ни Reverb, ни Redis-инфраструктуры под это; polling работает на текущем стеке без новых движущихся частей |
| Структура чата | Один диалог на покупателя (как переписка в Telegram) — не отдельный чат на каждый заказ |
| Кто отвечает от магазина | Владелец + администраторы (роли из раздела «Сотрудники»). Мастера — не участвуют, это не их зона ответственности |
| Вложения в v1 | Только фото. Файлы произвольного типа — отдельным шагом позже (см. «Файлы — что понадобится доделать») |

## 0. Что уже есть в проекте и на что это опирается

- **Мультитенантность**: у каждого магазина своя PostgreSQL-схема (`shop_{id}`). Все
  новые таблицы чата — per-tenant, как `customers`, `orders`, `products`.
- **Покупатель уже умеет логиниться**: `customer_sessions` (60 дней, мобильное
  приложение) и краткий `phone-token` (30 мин, веб-виджет) — см.
  `VerifyPhoneSession` / `VerifyPhoneToken`. Чат в мобильном приложении опирается
  на уже существующую сессию покупателя, ничего нового изобретать не нужно.
- **Роли на стороне магазина уже есть**: `ShopStaff.role` (`owner` / `admin` /
  `master`), see `SetShopFromAuth` — прописывает `staff_role` в атрибуты запроса.
  Чат просто добавляет ещё один экран, доступный `owner` и `admin`.
- **Загрузка изображений уже есть**: `ImageController::upload` (`/admin/upload/image`)
  и `Storage::disk('public')`. Для чата переиспользуем тот же диск и общий
  подход к загрузке — но не буквально ту же валидацию: у товарных фото это
  `image|max:1024` (грузит доверенная сторона — сам владелец магазина), а для
  чат-фото нужно немного строже, см. §5/П7.
- **Урок из недавнего бага (2026-08-22)**: ночная `storage:cleanup` удаляет любой
  файл в `uploads/`, если его URL не встречается ни в одной из отслеживаемых колонок
  БД. Когда чат появится — **обязательно** добавить колонку с URL фото сообщений в
  список `StorageCleanup::collectUsedPaths()`, иначе через сутки все фото в чатах
  исчезнут точно так же, как исчезали доп. фото товаров. Отдельный пункт в чек-листе
  ниже, чтобы не забыть второй раз.
- **Rate limiting уже есть паттерном**: `throttle:N,1` на маршрутах виджета
  (`discount/validate`, `reviews`, `analytics` и т.п.) — тот же подход для
  отправки сообщений.
- **Правило миграций**: как обычно — миграция создаётся, применяется, проверяется,
  переносится в `database/schema/pgsql-schema.sql`, файл миграции удаляется.
  Ниже сразу дана итоговая схема для `pgsql-schema.sql`, отдельных миграционных
  файлов в этом плане не будет.

## 1. Модель данных

Две новые таблицы в **каждой tenant-схеме** (рядом с `customers`, `orders` и т.д.
в `create_shop_schema()`):

```sql
-- chat_threads — один диалог = один покупатель этого магазина
CREATE TABLE %I.chat_threads (
    id                    UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    customer_id           UUID NOT NULL REFERENCES %I.customers(id) ON DELETE CASCADE,
    last_message_at       TIMESTAMPTZ,
    last_message_preview  TEXT,               -- первые ~80 символов последнего сообщения, для списка диалогов без JOIN
    unread_by_shop        INTEGER NOT NULL DEFAULT 0,   -- сколько непрочитанных магазином
    unread_by_customer    INTEGER NOT NULL DEFAULT 0,   -- сколько непрочитанных покупателем
    shop_last_read_at     TIMESTAMPTZ,        -- когда магазин последний раз открывал этот диалог — informational, НЕ источник статуса сообщения (см. §1.2)
    customer_last_read_at TIMESTAMPTZ,        -- аналогично для покупателя
    is_blocked_by_shop    BOOLEAN NOT NULL DEFAULT FALSE, -- магазин закрыл диалог (спам/абьюз), см. §6
    created_at            TIMESTAMPTZ DEFAULT NOW(),
    updated_at            TIMESTAMPTZ DEFAULT NOW()
);
CREATE UNIQUE INDEX ON %I.chat_threads(customer_id);  -- ровно один диалог на покупателя
CREATE INDEX ON %I.chat_threads(last_message_at DESC);

-- chat_messages — сообщения внутри диалога
CREATE TABLE %I.chat_messages (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    thread_id     UUID NOT NULL REFERENCES %I.chat_threads(id) ON DELETE CASCADE,
    sender_type   TEXT NOT NULL CHECK (sender_type IN ('shop', 'customer')),
    sender_staff_id UUID REFERENCES public.shop_staff(id) ON DELETE SET NULL, -- кто из сотрудников написал (null для sender_type='customer')
    client_message_id UUID,                   -- сгенерирован клиентом при отправке, см. §5.1 (защита от дублей при retry)
    body          TEXT,                       -- текст сообщения, может быть NULL если только фото, до 2000 символов
    image_url     TEXT,                       -- URL фото (Storage::disk('public')), NULL если только текст
    status        TEXT NOT NULL DEFAULT 'sent' CHECK (status IN ('sent', 'read')), -- единственный источник правды для статуса, см. §1.2; без промежуточного 'delivered' — см. §1.1 (П1)
    created_at    TIMESTAMPTZ DEFAULT NOW()
);
CREATE INDEX ON %I.chat_messages(thread_id, created_at);
CREATE UNIQUE INDEX ON %I.chat_messages(thread_id, client_message_id)
    WHERE client_message_id IS NOT NULL;  -- защита от дублей при retry, см. §5.1
```

Требование `body IS NOT NULL OR image_url IS NOT NULL` (сообщение не может быть
полностью пустым) — на уровне `CHECK`:

```sql
ALTER TABLE %I.chat_messages ADD CONSTRAINT chat_messages_not_empty
    CHECK (body IS NOT NULL OR image_url IS NOT NULL);
```

**Почему `sender_staff_id` ссылается на `public.shop_staff`, а не на tenant-таблицу**:
`shop_staff` — это `public`-схема (единая на все магазины, см. `SetShopFromAuth`),
как `shops` и `masters`-приглашения. Держим ссылку туда же, где и в остальном
проекте (см. `masters.user_id`, который указывает на `public.users`).

**Зачем `last_message_preview` и счётчики `unread_*` денормализованы в `chat_threads`,
а не считаются на лету** — список диалогов в админке (потенциально сотни
покупателей) должен открываться одним запросом без `COUNT()`/`ORDER BY MAX()` по
всем сообщениям каждый раз. Обновляются атомарно в той же транзакции, что создаёт
сообщение (см. §3).

## 1.1 Правки по итогам критического прогона (2026-08-23, до начала реализации)

Первая версия этого плана прошла собственную повторную проверку — вот что было
неточным или упущено, и как исправлено ниже по тексту:

## 1.2 Статус прочтения — единственный источник правды (П15, П16, §1.1)

Убираем двойную бухгалтерию. Правила:

- **`chat_messages.status`** — единственный источник правды для того, прочитано
  ли КОНКРЕТНОЕ сообщение. Клиент при отрисовке смотрит только на это поле,
  ничего не сравнивает сам.
- При вызове `/read` — один массовый `UPDATE`:
  `UPDATE chat_messages SET status = 'read' WHERE thread_id = ? AND sender_type = <чужая сторона> AND status = 'sent'`.
  Не по одному сообщению, один запрос на весь тред.
- **`shop_last_read_at`/`customer_last_read_at`** — вспомогательная метка
  времени в `chat_threads`, обновляется в том же вызове `/read`. Используется
  только для показа «когда последний раз открывали диалог» (если когда-нибудь
  понадобится), но **не** для вычисления статуса отдельного сообщения — это
  ответственность колонки `status`, и только её.
- **Атомарность счётчиков** (П16, §1.1): `unread_by_shop`/`unread_by_customer`
  меняются только атомарными SQL-операциями — `increment()`/`decrement()`
  (Eloquent) или `... = ... + 1` в сыром SQL, никогда через «прочитать текущее
  значение в PHP, прибавить, сохранить обратно» (классическая гонка потерянного
  инкремента при двух одновременных сообщениях). Сброс на `/read` — простой
  `SET unread_by_shop = 0` без условия «если не изменилось с момента чтения»:
  если сообщение приходит буквально в момент сброса, его собственный атомарный
  `+1` всё равно применится **после** — просядет максимум на один цикл polling,
  не потеряется совсем.

## 1.3 Переиспользование номеров телефона (П18, §1.1)

Не проблема чата как такового — системное допущение всего проекта: покупатель
идентифицируется по номеру телефона (`Customer::where('phone', ...)`), а
российские операторы переиспользуют номера после периода неактива (обычно
несколько месяцев). Если номер попадёт к новому человеку — он унаследует всю
историю прежнего владельца: заказы, адреса, и теперь ещё переписку с фото.
Это не новый риск, который создаёт чат — он уже существует для заказов и
адресов сегодня. Но чат ощутимо повышает ставки: личная переписка и фотографии
воспринимаются гораздо чувствительнее, чем список товаров в старом заказе.

**В рамках этого плана — не чиним**, потому что решение требует пересмотра
модели идентификации покупателя во всём проекте, а не только в чате, и это
отдельная задача, а не часть чата. Возможное направление на будущее (см.
«Другие возможные доработки»): периодическая анонимизация давно неактивных
покупателей (например, если 6+ месяцев ни одного заказа/входа — обезличивать
имя, адреса, чат и т.п., оставляя только обезличенную статистику для отчётов),
чтобы номер, когда его переиспользуют, доставался уже пустой карточке, а не
чужой истории.

## 2. Кто может писать первым

Правило простое и совпадает с тем, как это устроено у большинства магазинов
с чатом (Wildberries, Ozon, любой маркетплейс): **покупатель пишет первым**,
диалог создаётся при первом сообщении от покупателя. Магазин не может «постучаться»
в чат покупателю, который никогда не писал — это защита от спам-рассылок через
чат под видом личного диалога (у магазина уже есть Telegram/MAX-уведомления для
массовых сообщений, чат — не канал рассылки).

Реализация: `POST /widget/chat/messages` создаёт `chat_threads` под капотом при
первом сообщении, если его ещё нет. Магазину эндпоинт отправки сообщения **не
создаёт** тред — только отвечает в уже существующий (`404`, если покупатель ни
разу не писал).

**Гонка при создании треда** (П3, §1.1): наивный `firstOrCreate` по `customer_id`
не атомарен сам по себе — при двойном тапе «отправить» или retry после обрыва
связи два одновременных запроса могут оба не найти тред и оба попытаться его
создать, упершись в уникальный индекс `chat_threads(customer_id)`. Правильная
реализация — `INSERT ... ON CONFLICT (customer_id) DO NOTHING`, затем
`SELECT` треда (гарантированно найдётся — либо создан этим запросом, либо
конкурентным), а не голый `firstOrCreate`, который такой конфликт не ловит.

## 3. API

### 3.1 Мобильное приложение (покупатель)

**Только мобильное приложение в v1, не веб-виджет** (П6, §1.1). Причина —
у мобильного приложения сессия покупателя живёт 60 дней (`X-Phone-Session`,
см. `VerifyPhoneSession`), а у веб-виджета — 30 минут (`VerifyPhoneToken`,
одноразовая проверка «посмотреть мои заказы в этом сеансе»). Чат на
30-минутной сессии означал бы «вводите SMS-код заново каждые полчаса, чтобы
проверить, ответил ли магазин» — непригодно. Маршруты остаются под общим
префиксом `/widget/*` (это исторически общее пространство для всего
покупательского API, им уже пользуется и мобильное приложение — см.
`/widget/orders`, `/widget/phone/verify`), но требуют именно `X-Phone-Session`,
которую сегодня получает только мобильное приложение. Гость без регистрации
писать в чат не может (иначе некому будет доставить ответ при следующем
визите — сессия обезличена). Веб-виджет с чатом — отдельная задача на будущее,
см. «Другие возможные доработки».

Throttle везде здесь — именованный `chat-customer`, ключ по `X-Phone-Session`,
не по IP (см. §3.3), лимиты те же цифры, что указаны ниже (интерпретируются
как «в минуту»).

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/widget/chat` | Текущий диалог этого покупателя: список сообщений (пагинация `?before=<message_id>`, курсор резолвится в timestamp на сервере — см. §3.4; 30 штук за раз, самые новые первыми). Throttle 60/мин |
| `POST` | `/widget/chat/messages` | Отправить сообщение (`body` до 2000 символов и/или `image_url`, плюс `client_message_id` — см. §5.1). Throttle 20/мин |
| `POST` | `/widget/chat/read` | Отметить весь диалог прочитанным (сбрасывает `unread_by_customer`). Throttle 60/мин |
| `GET` | `/widget/chat/poll` | Лёгкий опрос: «есть ли новое с `?after=<message_id>`» (курсор — см. §3.4) — см. §4. Throttle 60/мин (при интервале 3с это 20 реальных вызовов в минуту — лимит с запасом, не мешает штатной работе, но не даёт долбить эндпоинт мимо клиентского таймера) |
| `POST` | `/widget/chat/image` | Загрузить фото для сообщения (переиспользует `ImageController`-паттерн, но без `svg` в разрешённых типах — см. §5), возвращает `url` для последующего `POST /messages`. Throttle 10/мин |

### 3.2 Админка (владелец/администратор)

Под `auth:sanctum` + `auth.shop` + `not.master` (мастера чат не видят) — как
остальные `/admin/*` маршруты.

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/admin/chat/threads` | Список диалогов, отсортирован по `last_message_at DESC`. Пагинация. Поиск по имени/телефону покупателя. Throttle `60,1` |
| `GET` | `/admin/chat/threads/{id}/messages` | Сообщения диалога (пагинация `?before=<message_id>`, курсор резолвится в timestamp на сервере — см. §3.4). Throttle `60,1` |
| `POST` | `/admin/chat/threads/{id}/messages` | Ответить в диалог (`body` до 2000 символов и/или `image_url`, `client_message_id` — см. §5.1). Throttle `20,1` |
| `POST` | `/admin/chat/threads/{id}/read` | Отметить прочитанным. Throttle `60,1` |
| `POST` | `/admin/chat/threads/{id}/block` | Закрыть диалог для покупателя (спам) — см. §6. Throttle `20,1` |
| `GET` | `/admin/chat/poll` | Опрос: «в каких тредах новые сообщения с последнего опроса» — один запрос на всю админку, не по треду (см. §4). Throttle `60,1` |

Throttle здесь ниже приоритетом, чем на покупательской стороне (это
авторизованные сотрудники, не анонимный внешний трафик), но нужен как defense
in depth — скомпрометированный токен сотрудника или баг в клиенте (бесконечный
цикл опроса) не должны иметь возможность неограниченно бить по БД.

Кто именно из сотрудников написал сообщение — видно в `sender_staff_id`, в
списке сообщений админка показывает имя сотрудника под сообщением (как в общем
почтовом ящике поддержки — Intercom/Crisp так и делают: видно, кто из команды
ответил).

## 3.3 Throttle по сессии, не по IP (П13, §1.1)

Покупатель на этих маршрутах авторизован не через Sanctum-guard, а кастомным
заголовком `X-Phone-Session` (`VerifyPhoneSession` просто кладёт `customer` в
атрибуты запроса). Для встроенного `throttle:N,1` это означает «пользователь
не аутентифицирован» — по умолчанию Laravel считает лимит по IP. У большинства
мобильных операторов в России — carrier-grade NAT: сотни разных покупателей
на одном внешнем IP. На редких запросах (проверить промокод раз в сессию) это
не имеет значения, но polling каждые 3 секунды — совсем другой профиль
нагрузки: один активный собеседник исчерпывает лимит и на всех соседей по
тому же оператору, которые ни при чём.

Решение — именованный rate limiter вместо голого `throttle:N,1`, ключ явно
задан как значение заголовка сессии, а не резолвится автоматически:

```php
// AppServiceProvider::boot()
RateLimiter::for('chat-customer', function (Request $request) {
    $key = $request->header('X-Phone-Session') ?? $request->ip();
    return Limit::perMinute(60)->by($key);
});
```

Маршруты используют `->middleware('throttle:chat-customer')` вместо
`throttle:60,1`. Откат на IP остаётся только как fallback, если заголовка
почему-то нет вообще (такой запрос и так будет отклонён `VerifyPhoneSession`
дальше по цепочке middleware, до контроллера не дойдёт).

## 3.4 Курсоры пагинации — по времени, не по ID (П14, §1.1)

`id` в обеих таблицах — `gen_random_uuid()`, то есть случайный, а не
последовательный. Пагинация вида «дай сообщения с id меньше такого-то» не
работает вообще — UUID не сортируется по времени создания. Правильно:

- Клиент по-прежнему передаёт `?before=<message_id>` (не обязан сам таскать
  сырые timestamp'ы) — но на сервере это разрешается в реальный курсор:
  1. `SELECT created_at FROM chat_messages WHERE id = ?` — найти timestamp
     того сообщения, которое клиент уже видел самым старым;
  2. `SELECT ... WHERE (created_at, id) < (?, ?) ORDER BY created_at DESC, id DESC LIMIT 30`
     — сравнение по паре `(created_at, id)`, а не только по `created_at`,
     на случай двух сообщений с одинаковым timestamp (доля секунды между
     двумя быстрыми сообщениями подряд).
- То же самое для `GET /poll?after=<message_id>` — без варианта «или
  timestamp», как было расплывчато сформулировано раньше: только
  `message_id`, сервер сам резолвит его в `created_at` тем же способом.

## 4. Механизм доставки (polling) — детали, а не просто «раз в N секунд»

Наивный polling («стучаться в сервер каждые 3 секунды всегда, пока открыт экран»)
не годится сам по себе — 5 исследованных источников сходятся на одном: каждый
запрос поднимает Laravel, бьёт в БД, тратит CPU впустую, если новых сообщений
нет. Поэтому — с оптимизациями, которые уже стандартны для polling-чатов:

| Правило | Как реализовано |
|---|---|
| Опрашивать, только пока экран чата открыт | Мобильное приложение стартует таймер в `initState` чат-экрана, останавливает в `dispose`. Не крутится в фоне приложения |
| Пауза, когда приложение свёрнуто | `WidgetsBindingObserver` на `AppLifecycleState.paused` останавливает polling, на `resumed` — сразу один запрос и перезапуск таймера. Тот же принцип, которым Livewire по умолчанию тормозит `wire:poll`, когда вкладка не в фокусе |
| Интервал | 3 секунды, пока открыт конкретный диалог (и в админке, и в мобильном). 15 секунд — фоновый опрос «есть ли вообще новые сообщения» для бейджа-счётчика в шапке, когда сам экран чата не открыт. **Это прикидка, не результат нагрузочного теста** (П4, §1.1) — ориентир для пересмотра: если у одного сервера одновременно окажется больше ~30–50 открытых диалогов разом (сумма по всем магазинам на сервере, не по одному шоперу), стоит замерить реальную нагрузку на БД и, если нужно, увеличить интервал или переходить на путь апгрейда ниже — не выдавать 3с/15с за проверенные числа |
| Экономный ответ | `GET /poll` возвращает не сами сообщения, а компактный маркер: `{has_new: bool, unread_total: int}` — тело чата подгружается отдельным вызовом `GET /messages`, только если `has_new = true`. Не гонять полный список сообщений на каждый тик |
| Один опрос на всю админку, не на диалог | `GET /admin/chat/poll` без `{id}` в пути — возвращает карту `{thread_id: unread_count}` по всем диалогам разом. Если открыт список диалогов (не конкретный чат) — опрашивается ровно этот один эндпоинт, не N эндпоинтов на каждый диалог в списке |
| Задержка отправленного сообщения | Отправка (`POST /messages`) — обычный запрос, не через polling; оптимистичное обновление UI (сообщение сразу появляется в своей ленте серым/полупрозрачным как «отправляется», подтверждается или красным крестиком при ошибке) — стандартный паттерн, который используют все мессенджеры |

Это даёт задержку доставки 0–3 секунды внутри открытого диалога — заметно
медленнее «мгновенного» Telegram (WebSocket), но для чата поддержки шопер↔покупатель
(не игровой чат, не групповой чат с десятками участников) это ощущается как
«практически мгновенно» в реальном использовании, при нулевой новой инфраструктуре.

**Путь апгрейда на WebSocket в будущем** (если станет тесно): весь API уже
спроектирован так, что переход не потребует менять контракт — `GET /messages`
и `POST /messages` остаются теми же, просто вместо `GET /poll` подключается
Laravel Reverb broadcast на событие `MessageSent`. Не блокирует текущую реализацию,
просто держим это в голове при именовании (`ChatMessageSent` — сразу как будущее
Laravel Event, даже если пока просто создаёт запись в БД).

## 5. Фото в сообщениях

1. Покупатель/сотрудник выбирает фото или делает снимок камерой (неважно, какого
   размера файл с устройства) → **обязательно сжимается на клиенте** перед
   отправкой, до **100 КБ**. Не «до разумного размера», а до конкретной цифры
   (П20, §1.1) — это уже устоявшийся приём в проекте: админка сжимает фото
   товаров этим же способом до отправки (`useImageCompression.ts` →
   `compressIfNeeded`, обложка — 1 МБ/1920px, галерея доп. фото — 200 КБ/1280px).
   Для чата используем ТУ ЖЕ функцию `compressIfNeeded` с целью `0.1` МБ и
   стороной ~1024px (жёстче галереи, потому что фото в переписке маленькое и
   мимолётное, не карточка товара, которую разглядывают крупно).
   - **Веб (админка)** — `compressIfNeeded(file, { maxSizeMB: 0.1, maxWidthOrHeight: 1024 })`,
     функция уже существует и переиспользуется, ничего нового писать не нужно.
   - **Мобильное приложение (Dart)** — аналогичной готовой переиспользуемой
     функции пока нет, нужно завести (`compressChatImage()` в `mobile/lib/core/`)
     на пакете `flutter_image_compress` с теми же параметрами (0.1 МБ / 1024px),
     по аналогии с тем, как уже сжимается фото профиля (см. существующий
     аплоад аватара, если он уже сжимает — переиспользовать тот же подход,
     не плодить два независимых механизма сжатия в мобильном приложении).
2. `POST /widget/chat/image` (или `/admin/chat/image`) — **никакой проверки
   размера файла и никакого сообщения пользователю про размер** (уточнено
   2026-08-23, П20.1 — исходная формулировка «потолок 150 КБ с ошибкой при
   превышении» была неверной трактовкой задачи). Каким бы огромным ни был
   файл — сервер сам гарантированно пересжимает его до ≤100 КБ через
   `ImageCompressionService` (GD: decode → resize ≤1024px → JPEG со
   ступенчато падающим качеством, при необходимости — повторное уменьшение
   стороны), а не отклоняет с ошибкой. Клиентское сжатие (шаг 1) — это про
   экономию мобильного трафика ДО отправки, а не про предотвращение отказа;
   серверное сжатие — независимая гарантия результата, работает даже если
   клиент почему-то не сжал вообще. Единственный потолок — общий лимит PHP
   на входящий запрос (`upload_max_filesize`/`post_max_size` в `Dockerfile`,
   25/30 МБ, и `client_max_body_size 15M` на nginx поверх — см. `deploy.sh`)
   — это инфраструктурная защита от откровенного DoS, не бизнес-правило,
   которое видит пользователь. Проверено вживую: синтетическое «фото» 36 МБ
   (специально плохо сжимаемое — шум, не гладкие цвета) сжалось до 63 КБ за
   0.58 сек; реальный JPEG 1.5 МБ, отправленный через настоящий HTTP-запрос
   — до 86 КБ, без единой ошибки на пути.
3. Клиент вызывает `POST .../messages` с этим `url` в `image_url`.
4. Пока фото грузится — в ленте локально показывается превью с индикатором
   загрузки (`isAttachmentUploading`-паттерн, как в готовых чат-SDK) — сообщение
   реально уходит на сервер только после того, как файл долетел.

**Почему не голое правило `image` (П7, §1.1)**: у товарных фото (`ImageController::
upload`) валидация — просто `image`, а стандартное `image`-правило Laravel по
умолчанию включает `svg` в список разрешённых расширений. Для товарных фото это
не страшно — их загружает сам владелец магазина себе же в каталог, доверенная
сторона доверяет сама себе. В чате — наоборот: файл грузит **посторонний
покупатель**, а откроет его **сотрудник магазина** у себя в браузере/приложении.
SVG может содержать `<script>` — тот же файл, который безобиден в контексте
товарных фото, становится вектором XSS в контексте чата, потому что меняется
направление доверия. Поэтому для чат-фото явно перечисляем разрешённые типы без
`svg`, а не полагаемся на дефолтное правило `image`.

**⚠️ Реальный баг, найденный при живом тесте реализации Ч2 (2026-08-23)**:
запись `image:jpeg,png,gif,webp` в валидации — синтаксическая ошибка. Правило
`image` в Laravel вообще **не принимает параметров** — это фиксированный
ярлык на `mimes:jpg,jpeg,png,bmp,gif,svg,webp` целиком, и всё, что после
двоеточия, молча игнорируется. Проверено буквально: залит `.svg` с `<script>`
внутри — прошёл валидацию как ни в чём не бывало. Правильно — правило
`mimes:...` само по себе, без `image` рядом. Это уже исправлено в реализации,
здесь фиксируем на будущее, если валидацию когда-нибудь будут переписывать —
чтобы грабли не наступили второй раз.

**GIF — не поддерживаем совсем** (П21, §1.1): проверил обе библиотеки сжатия,
которые проект уже использует или планирует использовать —
`browser-image-compression` (админка) официально не сжимает GIF, а
`flutter_image_compress` (мобильное) умеет только ДЕКОДИРОВАТЬ GIF, но
кодирует результат исключительно в JPEG/PNG/WebP, то есть на выходе анимация
всё равно потеряется (превратится в один статичный кадр) — сжатие «в GIF» ни
там, ни там не работает. Раз честно сжать GIF до 100 КБ с сохранением
анимации нечем — GIF просто убран из списка разрешённых типов. Разрешены
только `jpeg`, `png`, `webp` — то, что реально поддаётся сжатию тем же
механизмом, что уже есть в проекте.

**Открытие фото на весь экран** — тап по миниатюре в чате открывает то же самое
модальное превью, что уже используется в галерее товара (`_ProductGallery` в
`product_detail_screen.dart`) — переиспользуем компонент, не пишем второй раз.

## 5.2 Удаление сообщения с фото — файл должен удаляться из хранилища (П22, §1.1)

В исходной версии плана не было вообще никакой возможности удалить отдельное
сообщение — только полная блокировка треда (§6). Раз должна появиться
возможность удалить фото из чата, значит должна появиться и операция удаления
сообщения, а вместе с ней — обязательство подчистить файл на диске, а не
только строку в БД.

- **`DELETE /admin/chat/threads/{id}/messages/{message_id}`** — модерация
  силами владельца/администратора: удалить конкретное сообщение (например,
  неприемлемое фото от покупателя). Мягкое или жёсткое удаление — жёсткое:
  раз это модерация (не «я передумал» у самого отправителя), скрывать текст
  под пометкой «сообщение удалено» смысла нет, строка удаляется из
  `chat_messages` целиком.
- **Обязательно**: если у удаляемого сообщения есть `image_url`, тут же
  вызывается `StorageService::deleteByUrl($message->image_url)` — тот же
  готовый метод, что уже используется для аватаров и фото сотрудников
  (`ProfileController::deleteAvatar`, `StaffController::update`), не
  изобретаем второй способ. **Это именно тот класс бага**, из-за которого уже
  дважды пропадали/зависали файлы в этом проекте (`StorageCleanup` не знал
  про `product_images.url`, потом про `customers.avatar_url`, см. §0) — только
  наоборот: не «файл лежит, а БД про него не знает», а «БД забыла про
  сообщение, а файл остался висеть на диске мёртвым грузом навсегда». И то,
  и другое — рассинхрон между БД и диском, оба класса нужно закрывать явно,
  каждый раз при добавлении новой возможности удаления.
- Отдельный вопрос на будущее (не блокирует v1): нужна ли покупателю
  собственная кнопка «удалить моё сообщение» (аналог «удалить для всех» в
  Telegram/WhatsApp) — сейчас в плане такой возможности нет, удаление —
  только модерация магазином. Если понадобится самостоятельное удаление
  покупателем — это отдельная задача с отдельным вопросом (окно времени на
  удаление? видно ли собеседнику плейсхолдер «сообщение удалено»?).

## 5.1 Защита от дублей при повторной отправке (П8, §1.1)

Проблема: покупатель нажимает «Отправить», запрос уходит, но из-за плохой сети
ответ не долетает обратно (или клиент решает, что запрос завис) — приложение
показывает ошибку и предлагает повторить. Если сообщение на самом деле уже
создалось на сервере, повтор создаёт **дубль** — та же проблема, что уже
однажды всплывала с состоянием заказа при обрыве связи в других частях проекта.

Решение — клиент сам генерирует `client_message_id` (UUID) один раз при
формировании сообщения (до первой попытки отправки) и передаёт его в каждой
попытке `POST /messages`, включая повторы. На сервере — уникальный индекс
`chat_messages(thread_id, client_message_id)` (см. §1 схема): при конфликте
`INSERT ... ON CONFLICT DO NOTHING`, а в ответе всё равно возвращается
существующее сообщение (не ошибка) — с точки зрения клиента повтор с тем же
`client_message_id` идемпотентен, что бы ни случилось на сети.

## 6. Модерация и защита от абьюза

- **Rate limit на отправку**: `throttle:20,1` (20 сообщений в минуту) — так же,
  как у остальных публичных виджет-эндпоинтов. Не даёт устроить flood одной
  стороне на другую.
- **Блокировка диалога магазином**: `is_blocked_by_shop` — если покупатель пишет
  спам/оскорбления, владелец жмёт «Заблокировать» в шапке диалога. После этого
  `POST /widget/chat/messages` для этого покупателя отвечает `403` с понятным
  сообщением («Магазин ограничил переписку»). Сама история переписки не удаляется —
  просто новые сообщения от покупателя перестают приниматься. Разблокировка —
  та же кнопка в состоянии toggle.
  **Явно** (П17, §1.1): блокировка останавливает только отправку. `GET /widget/chat`
  (чтение истории) продолжает работать как обычно — покупателю не закрывают
  доступ к уже полученным от магазина ответам (например, «доставим завтра до
  18:00», отправленный до блокировки, всё ещё должен быть виден). Блокируется
  именно возможность писать новое, а не факт существования диалога.
- **Никакой отправки файлов из чата товару/заказу не подмешиваем** — чат физически
  не может стать вектором для «прислать поддельный чек» и т.п., потому что оплата
  и статусы заказа как были, так и остаются исключительно через ЮKassa/админку —
  чат ничего не меняет в заказе, это чисто переписка.

Ссылаясь на найденный паттерн «shared team inbox» (Intercom/Crisp — общий
почтовый ящик, куда видят и отвечают все сотрудники с доступом): двухколоночный

```
┌─────────────────────┬──────────────────────────────────────┐

│  (слева, ~320px)     │                                       │

│  ● Артём Иванов   2   │  Здравствуйте! А до завтра            │
│    А до завтра дост..│  доставите заказ?              14:02  │
│    14:02              │                                       │
│                       │        Да, конечно, привезём завтра  │
│  ○ Мария Петрова      │        до 18:00     14:05 ✓✓ Оля      │
│    Спасибо!           │                                       │
│    вчера              │  [фото] Вот подтверждение оплаты      │
│                       │                                 14:06 │
│  ○ Сергей Смирнов     │                                       │

│    2 дня назад        │  │ Напишите сообщение...    📎  ➤  │ │
│                       │  └─────────────────────────────────┘ │
└─────────────────────┴──────────────────────────────────────┘
```

- **Список диалогов**: непрочитанные — жирным + цветная точка + бейдж-счётчик
  (`●` = есть непрочитанные, `○` = прочитано), последнее сообщение — серым,
  превью в одну строку, время/дата справа по паттерну «Сегодня — время,
  иначе — дата» (тот же принцип, что уже реализован в `formatShortDate`,
  переиспользуем).
- **Пункт меню «Чат»** в `AppLayout.vue` (`navigation` массив) — с бейджем общего
  числа непрочитанных сообщений по всем диалогам (число в кружке рядом с
  пунктом меню, как непрочитанные письма в любом почтовом клиенте). Источник
  числа — тот же `GET /admin/chat/poll`, который уже опрашивается для списка.
- **Бейдж на вкладке браузера** (П5, §1.1): пока есть непрочитанные, `document.title`
  меняется на `«Чат (3) — ServiceBox»` (`favicon`/title обновляются через
  `document.title = ...` при каждом опросе `/admin/chat/poll`, независимо от того,
  какой раздел админки открыт сейчас — не только на странице чата). Владелец
  магазина обычно держит админку фоновой вкладкой браузера и не смотрит на неё
  постоянно — цифра в заголовке вкладки (тот же приём, что у Gmail) — единственный
  шанс заметить новое сообщение, не переключаясь на вкладку.
- **Контекст покупателя в шапке диалога** (П11, §1.1): рядом с именем и телефоном —
  количество заказов и сумма покупок (`total_orders`/`total_spent`, те же поля,
  что уже отдаёт `ProfileController` покупателю про самого себя — переиспользуем
  для сотрудника, не считаем заново). Сотруднику не нужно переключаться на
  вкладку «Клиенты», чтобы понять, постоянный это покупатель или новый.
- **Открытый диалог**: сообщения магазина — выровнены вправо (фирменный
  `primary_color` магазина — тот же паттерн, что уже используется в виджете/
  мобильном приложении: `ColorScheme.fromSeed` от цвета шопера), сообщения
  покупателя — влево, серые. Группировка по дате (разделитель «Сегодня» /
  «21 августа») — стандартный паттерн, подтверждённый исследованием (Telegram/
  iMessage). Под сообщением магазина — маленькая подпись имени сотрудника,
  если ответил не владелец (`sender_staff_id` → имя из `shop_staff.user.name`).
- **Статусы сообщений**: галочка — на СВОИХ исходящих сообщениях (кто их
  видит — по стороне: в админке это сообщения магазина, в мобильном
  приложении — симметрично, сообщения покупателя, см. ниже §8). Один серый
  чек `✓` — `chat_messages.status = 'sent'`, два синих `✓✓` —
  `status = 'read'` (единственный источник правды — см. §1.2; массово
  проставляется при вызове `/read` на стороне читающего). У чужих входящих
  сообщений галочки не нужны — сторона и так видит, что читает их прямо
  сейчас. Без промежуточного «доставлено» (П1, §1.1) — статус, завязанный на
  факт опроса `/poll`, был бы фикцией: опрос мог случиться на любом экране
  приложения, не обязательно в чате, а без сети вообще никогда бы не наступил,
  хотя сообщение реально ждёт на сервере. Отправлено/прочитано — единственные
  два состояния, которые честно отражают происходящее.
- **Поле ввода**: текст + скрепка (фото) + кнопка отправки, идентично мобильному
  — общий визуальный язык.
- **Пустое состояние**: пока ни один покупатель не писал — «Пока никто не писал.
  Как только покупатель напишет в приложении, диалог появится здесь» (тот же тон,
  что у остальных пустых состояний в админке, см. `EmptyState`-паттерн в
  `DiscountsView`/`CustomersView`).

**Почему статус «прочитано» видят обе стороны** (решение изменено 2026-08-23):
первая версия плана прятала этот статус от покупателя по аналогии с B2B-чатами
поддержки (Intercom/Crisp скрывают его специально — управленческое решение
«шопер не хочет, чтобы клиент видел прочитанное-без-ответа»). Это было моей
собственной экстраполяцией чужого паттерна не по делу — задание изначально
просило интерфейс «по мотивам Telegram», а в Telegram галочки честно видят
обе стороны. Явное решение: показываем как есть, обеим сторонам, без
исключений — покупатель не должен быть человеком второго сорта в собственном
диалоге с магазином.

## 8. Интерфейс — мобильное приложение (Flutter)

### Точки входа в чат

- Иконка чата в шапке каталога (`CatalogScreen.appBar.actions`), рядом с

  бейджа, не изобретаем новый).

```
│ ←  Барбариска            🛒   │  ← шапка = название магазина + логотип,
```

- Пузыри сообщений: свои (покупателя) — справа, цвет `primary_color` магазина
  (тема уже приходит с сервера через `buildAppTheme`, см. `app_theme.dart` —
  ничего нового настраивать не нужно); сообщения магазина — слева, серые, с
  аватаром магазина (лого) у первого сообщения в группе подряд идущих
  (группировка последовательных сообщений одного отправителя — паттерн из
  исследования, чтобы не повторять аватар на каждой строке).
  Не показываем покупателю имя конкретного сотрудника — снаружи это должно
  выглядеть как «магазин ответил», а не «Оля ответила»: покупателю видно
  единое лицо магазина. Это отдельное, самостоятельное решение — не связано
  со статусом прочтения (см. ниже), который, наоборот, показываем честно.
  На **своих** сообщениях (то есть отправленных этим покупателем) — та же
  галочка, что и у магазина в админке: `✓` — `status = 'sent'`, `✓✓` —
  `status = 'read'` (единственный источник правды — см. §1.2). На чужих
  (входящих от магазина) — без галочки, как и в админке (см. §7, вайрфрейм
  выше уже это отражает).
- `ListView` с `reverse: true`, подгрузка старых сообщений при скролле вверх
  порциями по 30 (стандартный паттерн из исследования — не грузим всю историю
  разом).
- Поле ввода — как в `promo_code_field.dart`/`checkout` — `TextField` + иконка
  скрепки слева от поля (открывает `image_picker`, показывает превью выбранного
  фото над полем перед отправкой, с крестиком «убрать») + кнопка отправки справа,
  активная только когда есть текст или прикреплённое фото.
- Оптимистичная отправка: сообщение сразу появляется в ленте с лёгкой прозрачностью
  и маленьким спиннером вместо галочки, по ответу сервера — спиннер сменяется
  на серую `✓` (отправлено), синеет до `✓✓`, когда следующий `/poll` покажет,
  что магазин прочитал; если запрос упал — красный восклицательный знак с
  возможностью тапнуть и повторить отправку (тот же `client_message_id`, что и
  в первой попытке — см. §5.1, повтор не создаст дубль) — тот же UX, что в
  WhatsApp/Telegram при потере сети.
- Бейдж на иконке чата в шапке каталога — обновляется тем же фоновым polling
  (15 сек, см. §4), что уже будет крутиться для остального (не заводим второй
  независимый таймер).

- **Общий rate-limit бакет на 8 роутов чата админки** — голый `throttle:N,1` для авторизованного пользователя строит ключ только из `sha1(user_id)`, без учёта роута, поэтому polling (messages каждые 4с + список тредов каждые 10с + бейдж каждые 15с — 40+ запросов/мин сам по себе) съедал общий счётчик и блокировал отправку сообщений с ошибкой «Too Many Attempts» (нелокализованной). Исправлено именованными `RateLimiter::for()` бакетами по назначению (`chat-admin-read/write/moderate/image`) + русский текст на 429 для всех чатовых лимитеров, коммит `52ab595`.
- **Удалённое сообщение не пропадало из уже открытого чата** — poll умел только добавлять новые сообщения, никогда не убирал те, что пропали с сервера (модерация). Исправлено на обеих сторонах — poll теперь сверяет окно последних ~30 сообщений и убирает исчезнувшие, коммит `abd4a33`.

### 11.0 Что подтверждено исследованием (Telegram Desktop/Mobile, WhatsApp)

Референс-скриншот пользователя — WhatsApp (не Telegram, но семейство паттернов
то же самое: зелёная тема, `Ответить`/`Переслать` внизу, кружки-чекбоксы). Ниже —
что на самом деле делают оба мессенджера, и где я осознанно отступаю от буквального
задания (с пометкой почему):

- **Долгое нажатие / правый клик** — общий вход в режим выбора **и** мгновенное
  контекстное меню одного сообщения одновременно (см. §11.1/§11.2) — это то же
  самое событие, разное поведение по платформе.
- **Свайп вправо = «Ответить»** — это отдельное, самостоятельное действие на
  **одном** сообщении, не связанное с режимом множественного выбора. Работает
  всегда, даже когда ничего не выделено. Подтверждено — реализуем как просили.
- **Свайп влево = «Удалить»** — **вот тут ни Telegram, ни WhatsApp так не делают**.
  Свайп влево на пузыре сообщения нигде не привязан к удалению в обоих
  мессенджерах (свайп влево на **строке списка диалогов** — да, архивирует/удаляет
  чат целиком, но не отдельное сообщение внутри переписки). Причина, скорее всего,
  та же, что важна и нам: удаление сообщения — необратимое действие (у нас в
  проекте — жёсткое, файл с диска стирается навсегда, без «отменить»), и ни один
  крупный мессенджер не даёт стереть что-то навсегда одним быстрым жестом без
  подтверждения. Моя рекомендация (см. §11.3): свайп влево **приоткрывает** красную
  кнопку «Удалить» (не удаляет сам по себе), тап по ней — обычное окно
  подтверждения, которое в проекте уже есть и переиспользуется (`showConfirmDialog`
  на мобильном, тот же паттерн в админке). Если хотите буквально «долистал до
  конца — сразу удалилось», скажите — сделаю, но это будет первый жест
  безвозвратного удаления без подтверждения во всём проекте, и я бы не советовал.
- **Множественный выбор → «Ответить»** — в WhatsApp кнопка «Ответить» внизу
  показывается **только когда выбрано ровно одно** сообщение (ответить сразу на
  несколько технически бессмысленно — на какое из них тогда цитата?). При выборе
  двух и более — остаются только «Скопировать»/«Удалить» (и «Переслать», но см.
  ниже). Делаем так же.
- **«Переслать» — сознательно не включаю в план.** В WhatsApp/Telegram это отправка
  сообщения в **другой** чат — у нас в проекте один диалог = один покупатель,
  «переслать» было бы некуда (нет списка других тредов, куда переслать сообщение
  из чата с Афанасием). Если в будущем появится идея вроде «переслать вопрос
  покупателя другому сотруднику как заметку» — это отдельная фича, не буквальный
  «Переслать» из мессенджера, и не входит в этот раунд.
- **Свайп — это жест тачскрина.** У мыши на десктопе (админка) свайпа не бывает
  ни в одном настольном мессенджере (Telegram Desktop, WhatsApp Web, Slack) —
  тянуть мышью по тексту сообщения уже занято под выделение текста для
  копирования, так что «эмулировать свайп мышью» конфликтовало бы с этим и
  ощущалось бы чужеродно. Настоящий десктопный эквивалент свайпа-ответа — маленькая
  иконка-стрелка, всплывающая при наведении курсора на пузырь (Telegram Desktop
  делает ровно так), клик по ней = «Ответить». Реализуем так (см. §11.2).

### 11.1 Режим выбора — мобильное приложение (долгое нажатие)

Точно по референсу пользователя:

1. Долгое нажатие (`GestureDetector.onLongPress`, с лёгкой haptic-отдачей —
   `HapticFeedback.mediumImpact()`, как уже наверняка стоит на других долгих
   нажатиях в проекте, если есть — иначе просто `.selectionClick()`) на любом
   пузыре → вход в режим выбора.
2. Пузырь, по которому нажали, сразу выбран: сдвигается на ~12px в сторону
   чекбоксов (внутренняя `AnimatedPadding`/`AnimatedContainer`, ~180мс,
   `Curves.easeOut`), фон пузыря слегка темнеет (`Color.alphaBlend` с чёрным на
   ~6-8% — едва заметно, не должно выглядеть как ошибка рендера), слева от него
   вырастает зелёный кружок с галочкой (`AnimatedScale` из 0 → 1, ~150мс, лёгкий
   overshoot — `Curves.easeOutBack`, тот самый «пружинистый» попап, что в
   Telegram/WhatsApp).
3. У всех остальных пузырей одновременно появляются пустые кружки слева
   (`AnimatedOpacity` 0→1, ~150мс) — тап по пустому кружку добавляет сообщение
   в выбор (та же анимация превращения в зелёную галочку).
4. `AppBar` каталога/чата подменяется на `SelectionAppBar`: крестик слева
   («выйти из режима выбора, сбросить»), «Выбрано N» по центру, три иконки
   справа — Копировать / Редактировать / Удалить. Редактировать — только когда
   выбрано ровно одно **своё** сообщение с текстом (не чужое, не только фото).
   Переход шапки — `AnimatedSwitcher` со сдвигом сверху, ~200мс.
5. Внизу экрана — плавающая кнопка «Ответить» по центру (`AnimatedSlide` снизу),
   видна только когда выбрано ровно одно сообщение (любое, не обязательно своё).
6. Выход из режима: крестик, либо снятие последнего чекбокса (когда выбор
   опустел, режим сам закрывается — обычное поведение), либо системная кнопка
   «назад».

### 11.2 Режим выбора и быстрые действия — админка (правый клик)

Разница с мобильным: у мыши есть точный клик, поэтому не обязательно сначала
входить в отдельный «режим выбора» ради одного действия — как в Telegram Desktop:

1. **Правый клик по пузырю** (`@contextmenu.prevent`) → мгновенное контекстное
   меню у курсора: Ответить, Скопировать, Редактировать (свои сообщения с
   текстом), Удалить, разделитель, **Выбрать** — без входа в массовый режим,
   для одного сообщения это самый быстрый путь.
2. Пункт **«Выбрать»** (или клик по чекбоксу, который всплывает при наведении
   слева от пузыря, `opacity: 0 → 1` на `:hover`, ~120мс — так же as в Telegram
   Desktop) — включает режим множественного выбора: слева от каждого пузыря
   появляются кружки-чекбоксы (та же логика, что в §11.1, просто по клику, не
   по тапу), верхняя панель диалога подменяется на «Выбрано N» + иконки
   Копировать/Удалить (Редактировать и Ответить — не бывают массовыми, см.
   §11.0), `<Transition>` — те же 5 переходов уже используются в других местах
   `admin/src`, ничего нового заводить не нужно, стиль будет узнаваемым.
3. **Наведение на пузырь без правого клика** — маленькая иконка-стрелка «ответить»
   всплывает у внешнего края пузыря (`opacity`+`transform: translateX`, ~120мс) —
   это и есть десктопный эквивалент свайпа-вправо из задания. Клик — то же самое,
   что «Ответить» из контекстного меню.

### 11.3 Свайп (мобильное) — детали жеста и анимация

- **Вправо → «Ответить»**: `GestureDetector.onHorizontalDragUpdate` на каждом
  пузыре (не `Dismissible` — тот только для полного смахивания «в никуда», тут
  нужен **частичный** свайп с пружинным возвратом). Порог срабатывания — как в
  Telegram, ~60-70px протяжки; в процессе перетаскивания сам пузырь чуть сдвигается
  вправо (не дальше ~80px, дальше — сопротивление), сбоку проявляется иконка
  стрелки-ответа, растущая по мере протяжки. Отпустили после порога → короткая
  haptic-отдача + пузырь пружинисто (`Curves.elasticOut`, ~250мс) возвращается на
  место, сообщение становится «цитатой» над полем ввода. Отпустили до порога —
  просто плавный возврат без действия.
- **Влево → приоткрыть «Удалить»** (см. §11.0 про отказ от мгновенного удаления):
  свайп влево до ~72px открывает и фиксирует красную зону с иконкой корзины
  сбоку от пузыря (как список писем в Gmail/Apple Mail — свайп **открывает**
  кнопку действия, а не выполняет действие сам по себе). Тап по красной зоне →
  обычное окно подтверждения (`showConfirmDialog`, уже есть в проекте). Тап
  мимо/повторный свайп вправо — зона задвигается обратно.
- Обе анимации — на `AnimationController` с `SingleTickerProviderStateMixin`
  на каждом пузыре (или общий контроллер списка с индексами — решается на этапе
  реализации, не влияет на план).

### 11.4 Ответ на сообщение (Reply)

- Новая колонка `chat_messages.reply_to_message_id` (nullable, `UUID`,
  `REFERENCES chat_messages(id) ON DELETE SET NULL` — если процитированное
  сообщение потом удалили, ссылка не должна ломать вставку новой строки;
  цитата в интерфейсе в этом случае показывает «Сообщение удалено», как в
  Telegram, а не пропадает молча).
- При отправке с `reply_to_message_id` — тонкая цветная полоска слева +
  укороченный текст/эскиз фото оригинала сверху **внутри** пузыря нового
  сообщения (стандартный вид цитаты). Тап/клик по цитате — прокрутка к
  оригиналу с кратким подсвечиванием (`flash` на фон пузыря, ~600мс) — если
  оригинал ещё в подгруженном окне сообщений; если нет — сначала подгружаем
  через `?before=`/`?after=` до нужного сообщения (то же, что уже умеет
  курсорная пагинация, см. §3.4).
- Пока пишется ответ — планка над полем ввода с превью цитаты + крестик
  «отменить ответ» (везде одинаковый UX — Telegram, WhatsApp, Slack thread-reply).

### 11.5 Редактирование (только текст, только своё сообщение)

- Новая колонка `chat_messages.edited_at` (nullable, `TIMESTAMPTZ`) — модель
  сейчас явно отключает `updated_at` (`const UPDATED_AT = null`), трогать это
  не нужно, `edited_at` — отдельное поле, проставляется вручную в контроллере
  редактирования.
- Без ограничения по времени редактирования (как в Telegram, не как в WhatsApp
  с их 15 минутами) — проще, и это не публичный канал с миллионами читателей,
  где старое сообщение могли скопировать и разослать раньше, чем ты его
  поправишь.
- Редактировать может только автор сообщения: на стороне магазина — либо тот
  же `sender_staff_id`, что у отправителя (сотрудник не может поправить чужой
  ответ), либо владелец — правкой любого `sender_type = 'shop'` сообщения (у
  владельца `sender_staff_id` всегда `null`, отличить «своё» иначе нельзя) —
  **это открытый вопрос, см. §11.10, п.3**.
- Фото не редактируется (заменить картинку задним числом — не то, что делает
  «редактировать» ни в одном мессенджере). Подпись к фото — это и есть `body`
  того же сообщения, значит редактирование подписи уже работает через тот же
  один endpoint, отдельно ничего не заводим.
- В пузыре рядом со временем — мелкая пометка «изменено» (как Telegram), не
  показывающая историю правок (историю правок Telegram тоже не хранит просто
  так, только показывает факт).

### 11.6 Копирование

- Только текст (`body`), только клиент — `navigator.clipboard.writeText` в
  админке, `Clipboard.setData` во Flutter. Копирование изображения в системный
  буфер — отдельно, сложнее (нужны специфичные для платформы разрешения/API,
  выигрыш сомнительный) — **сознательно не включаю в v1**, можно добавить
  позже отдельным пунктом, если реально понадобится.
- При множественном выборе (несколько сообщений) — копируются тексты всех
  выбранных, в хронологическом порядке, через перевод строки между ними (то
  же поведение, что в Telegram при копировании нескольких сообщений сразу).
  Сообщения без текста (только фото) — просто пропускаются в этой склейке.

### 11.7 Звук нового сообщения

**Только пока чат открыт/приложение активно** — это принципиальное ограничение
по архитектуре, не забыл: в проекте вообще нет push-инфраструктуры (ни Firebase
Cloud Messaging, ни APNs — проверено 2026-08-23 при разборе предыдущего раунда,
см. «Другие возможные доработки» ниже), значит звук, когда приложение свёрнуто
или браузер закрыт/вкладка неактивна — отдельная, гораздо более крупная задача
(нужен весь FCM-стек), не входит в этот раунд. Внутри открытого чата/активной
вкладки — звук на **входящее** сообщение (не на своё исходящее, это не WhatsApp
на телефоне-«вибро»-звонилке) реализуется просто:

- **Админка**: предзагруженный `<audio>` (или `new Audio(url)`), `.play()` при
  обнаружении нового входящего сообщения на очередном тике poll (`chatStore.poll()`
  / `pollOpenThread()`). Единственная реальная сложность — политика браузеров
  против автовоспроизведения звука без действия пользователя: она блокирует
  звук **до первого клика/нажатия клавиши** на странице вообще, но админ уже
  залогинен и активно кликает по интерфейсу задолго до первого нового сообщения,
  так что на практике это не проблема (тот же паттерн работает в Intercom/Crisp/
  любой веб-панели поддержки). Добавляю переключатель «Звук уведомлений
  вкл/выкл» (persist в `localStorage`, тот же принцип, что уже используется для
  темы — `useTheme`) — принудительный звук без возможности выключить раздражает.
- **Мобильное**: нужен новый пакет — сейчас в проекте вообще нет ни
  `audioplayers`, ни `just_audio` (проверено). Беру `audioplayers` (самый
  распространённый, простой API) — воспроизведение короткого звука при
  обнаружении нового входящего сообщения в `_poll()` `ChatScreen`, только пока
  экран активен (`AppLifecycleState.resumed`, уже отслеживается через
  `WidgetsBindingObserver`, см. текущий код).
- **Нужен сам файл звука** — в репозитории сейчас нет ни одного `.mp3`/`.wav`
  (проверено). Либо вы подкинете готовый короткий сэмпл (типичная длина
  «дзынь»-уведомления — 200-400мс), либо я подберу лицензионно чистый короткий
  звук (например, из открытых источников вроде Google's Material sound
  resources — они под открытой лицензией и как раз для UI-уведомлений). Один и
  тот же файл переиспользуется в обоих приложениях — не изобретаем два разных
  звука для одной и той же сути.

### 11.8 Анимации — сводка

| Элемент | Анимация | Длительность |
|---|---|---|
| Вход в режим выбора (первый пузырь) | сдвиг + затемнение фона + попап галочки | ~150-200мс |
| Появление чекбоксов у остальных пузырей | fade-in | ~150мс |
| Смена шапки на «Выбрано N» | slide-down / `AnimatedSwitcher` | ~200мс |
| Кнопка «Ответить» снизу | slide-up | ~200мс |
| Свайп вправо (в процессе) | сдвиг пузыря + рост иконки-ответа | привязано к пальцу |
| Свайп вправо (отпустили) | пружинный возврат | ~250мс, `elasticOut` |
| Свайп влево (открыть удаление) | сдвиг + фиксация красной зоны | ~200мс |
| Новое сообщение появляется в ленте | scale+fade попап (как Telegram) | ~150мс |
| Цитата подсвечивается при переходе по клику | flash фона пузыря | ~600мс |
| Наведение → иконка ответа (админка) | opacity+translateX | ~120мс |

### 11.9 Изменения в бэкенде

- `chat_messages.reply_to_message_id UUID NULL REFERENCES chat_messages(id) ON DELETE SET NULL`
- `chat_messages.edited_at TIMESTAMPTZ NULL`
- Обе колонки — в `create_shop_schema()` **и** `ALTER TABLE IF NOT EXISTS`-циклом
  по уже существующим магазинам, по уже устоявшемуся в проекте правилу
  тенантных миграций, одним коммитом (без отдельного файла миграции, который
  потом надо не забыть удалить).
- Новый endpoint `PATCH /admin/chat/threads/{id}/messages/{message}` (и
  зеркальный `PATCH /widget/chat/messages/{id}`, если решим давать эту
  возможность и покупателю — см. §11.10, п.2) — обновляет `body`, проставляет
  `edited_at = now()`, отклоняет попытку редактировать чужое сообщение (403) и
  сообщение с `image_url`, но без `body` (нечего редактировать).
- `sendMessage`/store() — принимают необязательный `reply_to_message_id`,
  валидация `exists:chat_messages,id` **в пределах того же треда** (нельзя
  сослаться на сообщение из чужого диалога).
- Массовое удаление при множественном выборе — **без нового endpoint**: цикл
  вызовов уже существующего `DELETE .../messages/{id}` на клиенте, по одному
  на каждое выбранное сообщение. Проще, чем городить bulk-API ради операции,
  которая на практике редко затрагивает больше нескольких сообщений разом
  (не тысячи).
- Копирование — без изменений на бэкенде вообще (чистый клиент).

### 11.10 Открытые вопросы — нужно решение перед реализацией

1. **Свайп влево = мгновенное безвозвратное удаление, или приоткрыть кнопку +
   подтверждение (моя рекомендация, §11.0/§11.3)?**
2. **Может ли покупатель в мобильном приложении так же выделять/отвечать/
   копировать/редактировать/удалять СВОИ сообщения** (симметрично админке), или
   этот раунд — только для админки, а покупателю оставляем текущий простой
   экран без изменений?
3. **Если да — может ли покупатель удалить только своё сообщение, а магазин
   (модерация) — вообще любое в треде** (как сейчас), или как-то иначе?
4. **Звук уведомления** — жду от вас файл, либо разрешение подобрать самому
   лицензионно чистый короткий сэмпл.

## 12. WebSocket вместо polling — оценка трудозатрат

Прямой ответ на вопрос «как долго и сложно»: **реалистично 4-7 рабочих дней**
на аккуратную реализацию с тем же уровнем проверки вживую, что и весь чат до
сих пор (не «накидать за вечер и надеяться») — из них главная неожиданная
сложность не в самом WebSocket, а в том, что покупатель в этом проекте
авторизован нестандартно (см. ниже).

### Почему не «пара часов»

- **Инфраструктуры вообще нет** — ни Redis, ни очередей, ни broadcasting
  конфигурации (проверено: в `composer.json` нет ни `pusher`, ни
  `laravel/reverb`, ни `laravel/echo`, `config/broadcasting.php` не настроен).
  Начинать пришлось бы с нуля, не «включить то, что уже наполовину стоит».
- **Рекомендуемый вариант — Laravel Reverb** (официальный, бесплатный,
  self-hosted WebSocket-сервер от авторов Laravel, появился в Laravel 11) —
  не Pusher (платный SaaS) и не `laravel-websockets` (community-пакет,
  фактически в режиме поддержки после выхода Reverb). Реалистично разворачивается
  как ещё один контейнер в уже существующем `docker-compose` этого проекта.
- **Самое нетривиальное место — авторизация приватных каналов.** Стандартный
  Laravel Echo ожидает, что приватный канал авторизует Sanctum-залогиненный
  `$request->user()`. У сотрудников магазина это есть из коробки (Sanctum). А
  вот покупатель авторизован кастомным заголовком `X-Phone-Session`, а не
  через Sanctum-guard (см. §3.3 — та же особенность, что уже потребовала
  отдельного именованного rate limiter вместо обычного throttle) — значит
  под него нужен свой, руками написанный auth-callback для broadcasting-роута,
  который проверит `X-Phone-Session` вместо `Auth::user()`. Не невозможно,
  но именно эта часть съедает большую часть непредсказуемости оценки.

### Раскладка по объёму работы

| Часть | Что делать | Оценка |
|---|---|---|
| Инфраструктура | `laravel/reverb` в `composer.json`, контейнер `reverb` в `docker-compose`, nginx-конфиг с `Upgrade`/`Connection` заголовками для WebSocket-апгрейда (хостовый nginx уже терминирует TLS — нужен ещё один `location` под путь Reverb) | ~0.5 дня |
| Бэкенд | Событие `ChatMessageSent implements ShouldBroadcast`, приватный канал на тред (`chat.thread.{id}`), кастомный auth-callback канала для `X-Phone-Session` (нестандартная часть выше) | ~1-1.5 дня |
| Админка (Vue) | `laravel-echo` + `pusher-js` (Reverb говорит по Pusher-протоколу, тот же клиент подходит), подписка на канал открытого треда, замена / дополнение poll-логики на событие, реконнект при обрыве | ~0.5-1 день |
| Мобильное (Flutter) | Dart-клиент WebSocket/Pusher-каналов (экосистема беднее, чем JS — придётся либо взять менее популярный пакет, либо написать тонкую обёртку самому), переподключение с backoff, увязка с уже существующим `AppLifecycleState` (пауза/резюме) | ~1-2 дня — обычно самая капризная часть на практике |
| Сквозное тестирование | Живая проверка на реальном сервере: обрыв связи, разворот телефона в фон/обратно, два одновременных получателя, откат на polling при недоступности WebSocket (fallback) | ~0.5-1 день |

**Итого: 4-7 рабочих дней**, в зависимости от того, насколько гладко пойдёт
Dart-клиент на мобильном (самая непредсказуемая строка в таблице).

### Стоит ли делать сейчас

**Моя рекомендация — нет, не сейчас.** Причины:

- Нынешний polling (4 сек в открытом чате) уже создаёт ощущение «почти
  реального времени» для чата поддержки маленького интернет-магазина — это не
  биржевой тикер и не игра, где счёт на сотни миллисекунд.
- Работа из §11 (выбор/ответ/редактирование/удаление/звук) не зависит от
  транспорта вообще и даёт заметно больше пользы на затраченный час — имеет
  смысл сделать её первой, независимо от решения по WebSocket.
- WebSocket становится по-настоящему оправданным, когда появится хотя бы одно
  из: (а) заметный рост числа одновременных диалогов и жалобы на задержку,
  (б) желание индикатора «печатает…» (сейчас в списке идей на будущее ниже —
  он *требует* WebSocket или неприемлемо частого polling ради одного статуса),
  (в) push-уведомления в свёрнутом приложении (тоже отдельная задача, но раз
  всё равно придётся городить постоянное соединение с сервером для пуша,
  разумно делать оба сразу одним заходом).

Если решите делать — предлагаю отдельным этапом **после** §11, не вместе.

## 🔜 Файлы — что понадобится доделать (после фото, отдельный шаг)

Файлы произвольного типа (PDF, документы, видео) в v1 сознательно не включены —
решение принято 2026-08-23. Когда возьмёмся:

| # | Что |
|---|---|
| Ф1 | `chat_messages.file_url` + `file_name` + `file_size_bytes` + `file_mime_type` — отдельные колонки, не переиспользовать `image_url` (у файла есть имя и тип, у фото — нет) |
| Ф2 | Валидация MIME по белому списку (`pdf`, `doc(x)`, `xls(x)`, обычные архивы) — **никаких исполняемых расширений** (`.exe`, `.sh`, `.apk` и т.п.) — это была бы прямая дыра для распространения вредоносных файлов через доверенный канал «магазин прислал» |
| Ф3 | Лимит размера файла (вероятно 10–20 МБ) — сейчас лимит фото 2 МБ, для документов нужно больше |
| Ф4 | UI: иконка типа файла вместо превью-картинки (PDF-иконка, DOC-иконка и т.п.), имя файла + размер под иконкой — общий паттерн любого мессенджера |
| Ф5 | Скачивание файла на мобильном — через `path_provider`/`open_filex` или аналог, с проверкой разрешений на запись |

## 🔜 Другие возможные доработки — идеи на будущее, не начато

- **Push-уведомления о новом сообщении, когда приложение закрыто** — сейчас в
  проекте нет ни Firebase Cloud Messaging, ни другой push-инфраструктуры вообще
  (проверено 2026-08-23). Без polling-экрана открытым, покупатель не узнает о
  новом сообщении от магазина, пока сам не откроет приложение. Отдельная большая
  задача — подключение FCM для Android (RuStore-сборки — Android-only), не входит
  в объём текущего плана.
- **WebSocket вместо polling** — оценка трудозатрат (4-7 дней) и рекомендация
  отложить до появления реальной причины — см. §12.
- **Индикатор «печатает…»** — приятная мелочь из Telegram, но требует либо
  WebSocket, либо очень частого polling именно ради этого одного статуса —
  не оправдано на текущем этапе.
- **Поиск по тексту сообщений** — если история переписки вырастет, понадобится
  полнотекстовый поиск внутри диалога (Postgres `tsvector` — тот же принцип, что
  можно применить и к `products.name`/`description`, если когда-то понадобится
  поиск по каталогу умнее, чем `ILIKE`).
- **Чат в веб-виджете, не только в мобильном приложении** (П6, §1.1) — сейчас не
  входит в объём v1, потому что у веб-виджета нет долгой сессии покупателя
  (только 30-минутный `phone-token`). Понадобится либо завести такую же
  60-дневную сессию и для виджета, либо явно смириться с тем, что в виджете
  чат каждый раз требует новый SMS-код (хуже UX, но не невозможно).
- **Привязка сообщения к конкретному заказу** (П10, §1.1) — сейчас один общий
  диалог без контекста заказа: если у покупателя несколько активных заказов,
  сотруднику приходится самому уточнять, о каком заказе речь. Возможное решение
  на будущее — необязательное поле «прикрепить заказ» при отправке сообщения
  (как пересылка карточки заказа в мессенджере) — не входит в v1 намеренно,
  чтобы не усложнять первую версию до того, как понятно, насколько это вообще
  востребовано на практике.
- **«Решено»/«Архив» для списка диалогов** (П19, §1.1) — сейчас список плоский,
  сортировка по свежести последнего сообщения — единственная приоритизация.
  Работает нормально, пока диалогов десятки; при росте до сотен активных
  разговоров понадобится явное состояние треда (`chat_threads.status` —
  `open`/`resolved`), вкладки «Активные»/«Решённые» в админке (тот же паттерн,
  что у Intercom — «Open»/«Closed» conversations), и авто-возврат в «Активные»,
  если покупатель написал снова в уже «решённый» тред. Не входит в v1 — сначала
  нужно увидеть, действительно ли объём чатов у реальных магазинов дорастёт до
  того, что плоский список станет проблемой.
- **Переиспользование номеров телефона** (П18, §1.1, см. §1.3) — периодическая
  анонимизация давно неактивных покупателей, чтобы новый владелец переиспользованного
  номера не наследовал чужую переписку/адреса/фото. Не специфично для чата —
  затрагивает модель идентификации покупателя во всём проекте, отдельная задача.
