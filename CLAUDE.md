## Проект

- **Шоперы** — наши клиенты (владельцы магазинов, используют админку)
- **Байеры** — клиенты шоперов (покупатели, используют виджет)
- **Таймзона** настраивается в админке каждым шопером. Всё что связано со временем опирается на неё.
- Пользователь — электрик, не разработчик. Объяснять сложные вещи простым языком.

## Архитектура проекта

Четыре части в одном репозитории:

- `app/` — бэкенд, Laravel 11 (PHP 8.2). Модели, контроллеры, сервисы, middleware.
- `admin/` — SPA админки для шоперов. Vue 3 + Vite + TypeScript + Tailwind, Pinia, Vue Router.
- `widget/` — SPA виджета для байеров, встраивается на сайт шопера. Vue 3 + Vite + TypeScript + Pinia, без роутера — один магазин на странице (каталог/корзина/чекаут).
- `mobile/` — приложение байера, Flutter. White-label: один флейвор сборки = один шопер (см. `mobile/README.md`), а не мультитенантный клиент с выбором магазина.
- `database/schema/pgsql-schema.sql` — единый файл схемы БД (миграции сворачиваются в него и удаляются, см. «Код» ниже).

**Мультитенантность:** одна Postgres-схема на каждый магазин (`shop_<id>`), общие таблицы (`shops`, `shop_staff`, `customers`-аутентификация) — в схеме `public`. `TenantService::setContext()` / `setContextByApiKey()` переключает `search_path` перед каждым запросом.

**State management** — разный на каждой платформе, осознанно:
- Админка и виджет (Vue) — Pinia. В админке по стору на предметную область (`admin/src/stores/`: auth, orders, products, categories, bookings, chat), не один общий store. В виджете стейта меньше — один магазин на странице.
- Мобильное (Flutter) — `provider` + `ChangeNotifier` (`mobile/lib/state/`: auth_state, cart_state, catalog_state, chat_state, shop_state). Не Bloc/Riverpod — сознательный выбор под масштаб (один шопер на сборку, немного экранов), не общий стандарт по умолчанию.

**Разделение шоперы / байеры:**
- Бэкенд: `/api/admin/*` (Sanctum-токен, для шоперов и их сотрудников) и `/api/widget/*` (заголовок `X-Shop-ID` + API-ключ, публично, для байеров) — разные middleware-стеки, не общий guard с проверкой роли внутри.
- Фронтенд: `admin/` — только шоперы; `widget/` и `mobile/` — только байеры. Общего UI-кода между ними нет (разные технологии), общий контракт — только HTTP API.
- Роли внутри шопера — `shop_staff.role`: `owner` / `admin` / `master` / `collector`. У `master` и `collector` урезанный доступ реализован через allow-list middleware (`RequireNotMaster`, `RequireCollectorAccess` — явный список разрешённых маршрутов, всё остальное 403), а не через проверки роли по всему коду.

**Ключевые сущности:** `Shop` (public-схема) — владеет товарами/заказами/чатами в своей тенантной схеме → `Product` → `Order` → `OrderItem`; `ShopStaff` — сотрудник с ролью, привязан к `Shop`; `ChatThread` → `ChatMessage` — переписка магазин↔покупатель.

## Конвенции кода

- Избегать копипасты. Не должно быть одинаковых кусков кода.
- Переиспользовать готовые компоненты — конкретно:
  - Админка: `admin/src/shared/ui/` (UiModal, UiAvatar, UiSpinner и т.д.)
  - Виджет: `widget/src/components/` (примитивы с префиксом Sb — SbButton, SbField, SbSelect)
  - Мобильное: `mobile/lib/ui/widgets/` (по одному виджету на переиспользуемый паттерн интерфейса)
- API-слой:
  - Админка / виджет (TypeScript) — один класс-клиент на приложение: `admin/src/lib/api.ts` (`ApiClient`), `widget/src/lib/api.ts` (`WidgetApi`). Все HTTP-запросы идут только через него, не разбросаны по компонентам.
  - Мобильное (Dart) — repository-паттерн: абстрактный интерфейс (`*_repository.dart`) + реализация (`api_*_repository.dart`) поверх общего `mobile/lib/data/api_client.dart`. Экраны обращаются к интерфейсу, не к HTTP напрямую.
- Таймзона шопа — технически:
  - Хранится в `shops.timezone` (public-схема), настраивается в Настройках админки.
  - Бэкенд: `Carbon::now($shop->timezone ?? 'Europe/Moscow')` / `Carbon::createFromFormat(..., $timezone)` — везде, где считаются слоты записи, окна доставки, напоминания (`app/Console/Commands/SendBookingReminders.php`, `SendMorningDigest.php`).
  - Админка: `authStore.shop?.timezone || 'Europe/Moscow'` передаётся в `toLocaleDateString`/`toLocaleTimeString(..., { timeZone })` — никогда не полагаться на локальную таймзону браузера.
